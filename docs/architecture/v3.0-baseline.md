# V3.0 统一架构、域名与实施约定

版本：V3.0 文档基线。编写日期：2026-10-13。状态：待按七阶段逐步执行；没有任何部署或故障测试被预先标记为通过。

## 1. 项目范围与文件职责

### 1.1 已确认的技术方向

主环境为三台 ESXi 上的十台 Rocky Linux 10 节点，采用 kubeadm、containerd、Cilium、kube-vip、MetalLB、Envoy Gateway 与 Gateway API。存储采用 Rocky Linux 上由 cephadm 管理的外部 Ceph，通过 Rook External/Ceph CSI 接入，不使用 vSAN。

GitLab CI 与 Jenkins 均为完整实现，必须覆盖 Java、Rust、C、C++、C#、JS/TS、Python；共用 Harbor、Nexus、BuildKit、GitOps 与应用验收契约。Backstage、Crossplane、全部可观测性、安全、Serverless、多集群与高级计算方向均保留在实施范围。

### 1.2 本次交付与后续补充

本次 ZIP 只包含 Markdown 规划文档。文档中的脚本、Playbook、Chart、YAML、Pipeline、State 和实验报告路径表示后续应产生的交付位置，并不表示本次已经生成这些文件或已经执行成功。

后续在对应步骤下补充实际参数、操作命令、界面操作、配置文件和结果即可。不要修改稳定步骤编号；新增操作作为本步骤内容或新编号的扩展条目。计划目标、实际执行、验收证据三者分开保存。

## 2. 内部域名和公网域名

### 2.1 内部域名统一为 egon.local

集群外基础服务使用 openwrt.egon.local、dns.egon.local、registry.egon.local、git.egon.local、repo.egon.local、admin.egon.local。节点使用 cp01.egon.local、cp02.egon.local、cp03.egon.local、infra01.egon.local、infra02.egon.local、storage01.egon.local、storage02.egon.local、storage03.egon.local、worker01.egon.local、worker02.egon.local。

主集群 API 使用 api.k8s.egon.local。业务统一使用各服务.apps.egon.local，例如 demo.apps.egon.local、grafana.apps.egon.local。jenkins.egon.local、backstage.egon.local、keycloak.egon.local 可以作为统一网关上的内部平台入口；这些是内部域名，不意味着必须额外部署独立 VM。Ceph 管理与对象入口使用 ceph.egon.local、s3.egon.local，并映射到实际受控端点。

### 2.2 集群内部服务域为 cluster.egon.local

为了使 Service FQDN 同样以 egon.local 结尾，本版将 Kubernetes clusterDomain 具体化为 cluster.egon.local。服务全名采用 service.namespace.svc.cluster.egon.local。此项必须在首次 kubeadm 初始化前确认并统一写入配置，不作为运行中随意修改的参数。[配置依据](../reference/official-sources.md#k02)；[服务发现依据](../reference/official-sources.md#k07)。

CoreDNS 对 cluster.egon.local 提供集群服务解析，其他查询转给集群外 DNS。基础 DNS 管理 egon.local，不把整个 egon.local 转回 CoreDNS。所有 Helm Chart、Operator、Istio、SDK 和模板都要检查是否硬编码默认的 svc.cluster.local，并改为本项目的实际域。

### 2.3 .local 的兼容风险不能省略

.local 具有 mDNS 特殊语义，因此 egon.local 不是无条件等同于普通内部单播 DNS 后缀。本项目按用户选择保留它，在 Phase 00 专门实施 macOS 分域单播解析以及 Rocky、浏览器、VPN、构建镜像和各语言客户端的验证。[标准依据](../reference/official-sources.md#r01)。

验收必须使用实际系统解析器和业务客户端，不以直接向某个 DNS 发出一次查询成功作为全部通过。内部 CA 与 DNS 是独立问题：解析正确并不代表证书自动受信任。

### 2.4 公网域名统一为 egon.top

只为明确批准公开的应用创建 egon.top 子域，例如 demo.apps.egon.top、api.egon.top。域名所有权与 DNS API 权限在 Phase 00 核实；本文件不声称已替用户查询、配置或发布任何公网记录。

有公网域名不等于有公网 IP、入站端口或可用隧道。是否公开、如何入站、TLS 如何终止与回源都须单独验收。内部 GitLab、Harbor、Nexus、Kubernetes API、Ceph、数据库及监控管理界面默认不公开。内外应用即使落到同一网关，也必须分别匹配 Host、SNI、证书和授权。

### 2.5 证书与身份命名

egon.local 使用私有 CA，根私钥离线保存；egon.top 按实际 DNS 权限使用公有 CA/ACME。公有证书不覆盖 egon.local；单层通配证书不覆盖任意多层子域。内部 CA 信任需要分别进入系统、Java、容器运行时和其他客户端的适当位置。

SPIFFE/SPIRE 专题拟使用 egon.local 作为工作负载信任域，执行时核对实现。信任域不是 DNS 权威区，也不替代 Kubernetes RBAC。所有产品自己的内部通信域与平台 DNS 一致性都需检查。

## 3. 网络与地址

### 3.1 主集群网络

节点/管理网络为 192.168.9.0/24，Pod 网络为 10.244.0.0/16，Cilium 每节点 Pod 地址块为 /24。Service 网络为 192.168.20.0/24；192.168.20.1 留给 Kubernetes API Service，192.168.20.10 留给 CoreDNS，业务 ClusterIP 主要自动分配。

Service 网段不是物理 VLAN，无需建立家用路由器网关，也不应接入 DHCP。整个 Service /24 的容量有限，本版要求跟踪分配量，并以约 180 个已分配地址作为提前评估点，而非平台硬限制。开启大型模块前估算新增 Service；不足时优先减少闲置模块或放到第二集群，不把运行中扩 Service CIDR 当作轻松的常规步骤。

### 3.2 基础设施地址

192.168.9.10 为 OpenWrt，.11 为 DNS，.12 为 Harbor，.13 为 GitLab，.14 为 Nexus，.15 为管理机，.16 为独立备份接入预留，.17 为可选第二 DNS。是否有真实的外部备份设备不能只靠给 .16 分配一个地址来满足。

ESXi .61/.62/.63 与 iDRAC .51/.52/.53 保持不变。主网关暂以现有实际值为准，192.168.9.1 仅是待现场核实的常见候选。所有静态地址启用前核对 DHCP 保留和占用。

### 3.3 十节点与入口地址

cp01/cp02/cp03 对应 .101/.102/.103；infra01/infra02 对应 .104/.105；storage01/storage02/storage03 对应 .106/.107/.108；worker01/worker02 对应 .109/.110。

API VIP 使用 192.168.9.100，由 kube-vip 管理。业务 VIP 预留 .201–.220，第一条 MetalLB 主线先使用 .201–.210，默认网关入口可用 .201；.211–.220 留给不重叠的对照或扩展。kube-vip、MetalLB 与 Cilium 不得共同宣告同一地址。

### 3.4 第二集群与后续存储网络

第二集群 Pod CIDR 为 10.245.0.0/16、Service CIDR 为 10.96.0.0/16，节点 IP 与 API VIP 在启用前从已核实可用范围划出。跨集群网络要求唯一身份和无冲突路由，不能只创建几个 CRD 便视为连通。

Ceph 第一版共用节点网络。独立存储网、BGP、VLAN 和高速网卡都需真实硬件和配置能力；未经核实不假定现有交换机支持。所有 CIDR 都要与家庭网络、VPN 远端和容器桥接网络交叉检查。

## 4. 资源与放置

### 4.1 初始虚拟机规格

控制平面三台，每台 4 vCPU、8GB；Infra 两台，每台 6 vCPU、12GB；Storage/Ceph 三台，每台 8 vCPU、16GB；Compute 两台，每台 8 vCPU、16GB。合计 64 vCPU、128GB。后续可按资源扩大到用户原定十台各 8 vCPU/16GB 的目标。

OS、containerd、临时构建和 OSD 数据盘分开规划。十台各 1TB 是虚拟磁盘配置目标，不代表十台都立即占满物理存储，也不代表 Ceph 有 10TB 可用空间。业务持久化主要通过 CSI 申请，不随意散落到各节点本地目录。

### 4.2 三台 ESXi 的初始放置

ESXi01（128GB）放 cp01、storage01、infra01、worker01，节点配置内存合计 52GB；ESXi02（64GB）放 cp02、storage02、infra02，合计 36GB；ESXi03（64GB）放 cp03、storage03、worker02，合计 40GB。

集群外 OpenWrt、DNS、Harbor、GitLab、Nexus、管理机的起步预算分别为约 2、2、8、16、8、4GB，另计 vCenter、ESXi 自身和其他现有 VM 的实际占用。它们不是都必须集中 ESXi01；最终按宿主机余量和基础服务单点风险分布。配置总量能启动，不等于具备任意一台 ESXi 失效后接管所有 VM 的 N+1 余量。

### 4.3 实际故障域与存储约束

一个控制平面与一个 Ceph 存储节点分别落到每台 ESXi。物理位置通过台账与自定义节点标签同步；发生 vMotion 或手工迁移后更新标签。不同 Node 名称不代表不同物理故障域。

不使用 vSAN；ESXi 本地 Datastore 不自动提供跨宿主机共享 VM 磁盘。若 OSD 是 RAID5 上的 VMDK，允许功能实验，但 RAID 与虚拟化会改变故障语义和性能，不能宣称已验证裸盘故障容灾。不能在同一 Ceph 上保存其唯一恢复材料。

## 5. 主线、依赖与控制权

### 5.1 基础设施自举顺序

管理入口与基础网络先于 DNS/PKI，DNS/PKI 先于 GitLab/Harbor/Nexus，软件供应先于 Kubernetes。Ceph 主机可独立管理；Rook External 与 CSI 在 K8s 建成后接入。平台 API、网格、安全、观测等按各阶段逐步加入。

GitLab、Harbor、Nexus 和恢复工具在集群外且不依赖该 K8s/Ceph 才能启动。Jenkins Controller 可使用集群内 Ceph PVC，但不被要求在集群损坏时自救；集群外的受控恢复执行器负责这条路径。

### 5.2 资源所有权

OpenTofu 负责已划定的虚拟机与虚拟硬件；Ansible 负责主机配置；kubeadm 管理主集群生命周期；cephadm 管理外部 Ceph；Rook External/CSI 消费外部存储。Rook 内部 Ceph 使用另一批盘。

Argo CD 是主 GitOps。Crossplane 生成的资源由其管理，Argo CD 只管理顶层请求；数据库 Operator 再管理自身子资源。GitLab CI/Jenkins 通过同一 State 的锁交替管理 IaC，不并发 Apply 同一对象。Flux、Tekton、CAPI、MetalLB/Cilium 对照均有独立范围。

### 5.3 常驻与按需模块

基础网络、DNS、仓库、主 K8s、外部 Ceph、CSI、主要网关、最低 GitOps/监控/备份为常驻起点。数据库、双 CI、门户、日志和追踪按当时实验负载决定运行规格。

ELK 与 Loki、两套网格、Falco 与 Tetragon、第二集群、KubeVirt、Kubeflow 和分布式推理不要求同时常驻。按需不等于无备份直接缩到零：有状态多数派和持久数据按各系统流程停机、恢复或从已验证备份重建。

### 6.2 阶段顺序与回访

00 完成自举准备；01 建立核心集群；02 完成主网络和调度；03 提供持久存储和数据服务；04 建立双 CI 与平台工程；05 建立观测和 SLO；06 执行进阶、安全与恢复。

02 的完整网格身份可以在 06 回访，04 的自动指标灰度要在 05 可用后回访。01 的 StatefulSet 先验证稳定身份，03 才验证真实 PVC 持久化。基础备份与权限从 00/01 开始，06 不是第一次备份。BGP、GPU、嵌套虚拟化或第二集群条件不满足时标为阻塞而非删除范围。
