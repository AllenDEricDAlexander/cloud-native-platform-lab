# Phase 02｜云原生网络、调度与服务治理

文档版本：V3.0。状态：未执行。步骤数：45。

从可观测的基础通信开始，建立 Service、网关、证书、网络隔离和调度规则，再逐项比较 eBPF、负载均衡、出站治理与服务网格。

前置条件：Phase 01 的十节点、Cilium、CoreDNS 和基础应用已健康。高级网格身份、自动灰度指标和跨集群网络分别在 Phase 04–06 具备依赖后回访。

实施边界：先完成主网络与调度，再进入 Phase 03；高级对比实验不阻塞主线。不得同时让两个控制器宣告相同 VIP，也不得在无回退通道时更换主集群 CNI 模式。

## 02.01 核对网络路径与诊断基准

### 02.01.01 绘制实际通信与信任路径

实施内容：记录 Mac 到 API、Mac 到业务、Pod 到 Pod、Pod 到 Service、Pod 到仓库及节点到外网的路径。

过程安排：逐一确认经过的 DNS、网关、代理和证书，标注哪些流量应绕过 OpenWrt；为 Ceph 节点地址预留连通性检查。

完成判定：形成实际路径说明，排障时能区分 DNS、L2、路由、Service 转发和应用层。

### 02.01.02 建立跨节点连通性测试集

实施内容：在不同 ESXi 上运行轻量客户端与服务端，覆盖同节点、跨节点、跨命名空间和集群外客户端。

过程安排：分别测试 TCP、UDP、DNS 和必要的 HTTP/gRPC；记录 MTU、延迟和丢包，不用单个 Ping 代表全部应用协议可达。

完成判定：得到后续改动前的基准；网络切换后能够重复同一测试集对比。

### 02.01.03 启用 Hubble 基础观测

实施内容：配置 Cilium 流量观测、Relay 与受限入口，控制保留量和访问权限。

过程安排：在已知成功、超时和被策略拒绝的请求上验证流量记录；只在需要时启用更昂贵的 L7 观测。

完成判定：可用 Hubble 识别源、目标和拒绝原因，不把空白观测直接认定为没有流量。

## 02.02 完整验证 Service 与服务发现

### 02.02.01 验证 ClusterIP 与端点选择

实施内容：建立带标签选择器的 Service，观察其关联 EndpointSlice 与应用副本变化。

过程安排：修改 Readiness 和副本数，检查端点状态与新连接；明确 ClusterIP 是虚拟服务地址，不是可在 LAN 随意分配的接口。

完成判定：服务流量只进入符合条件的端点，应用使用 DNS 而非固定某个 Pod IP。

### 02.02.02 验证 NodePort 和流量策略

实施内容：在独立测试服务中暴露 NodePort，比较访问有无本地端点的节点以及不同外部流量策略。

过程安排：检查源地址、跨节点转发与主机防火墙；测试结束后关闭不再需要的 NodePort。

完成判定：能够解释 Local 与 Cluster 策略对流量与可用性的影响，节点端口未被过度暴露。

### 02.02.03 验证 LoadBalancer Service

实施内容：为业务申请受控 LAN VIP，记录 Service、负载均衡控制器和实际转发链路。

过程安排：先只暴露一个测试服务，观察 VIP 的 ARP 持有者与流量进入节点；不要把 IP 分配成功等同于数据面可达。

完成判定：Mac 能通过 VIP 访问服务，IP 回收和重新分配行为可验证。

### 02.02.04 验证 Headless 与无 Selector Service

实施内容：使用 Headless 观察直接端点发现；单独构造无 Selector 的服务发现实验。

过程安排：为后者建立受控的 EndpointSlice，区分手动维护外部端点与普通自动选择 Pod 的模式。

完成判定：能够说明无 ClusterIP 和无 Selector 是不同概念，手动端点具有明确维护责任。

### 02.02.05 验证 ExternalName 和 DNS 限制

实施内容：为测试客户端配置 DNS 别名型 Service，观察解析结果而不是期待它转发 TCP 流量。

过程安排：同时检查 HTTP Host、TLS SNI 与目标证书，避免别名解析成功但应用协议失败。

完成判定：理解 ExternalName 是 DNS 层映射，不提供反向代理、健康检查或证书自动替换。

### 02.02.06 验证集群域、搜索域和 DNS 缓存

实施内容：检查 cluster.egon.local、命名空间短名、FQDN、搜索域和应用解析行为。

过程安排：测量重复查询、负缓存和外部 DNS 延迟；NodeLocal DNSCache 作为可选对比，在基本路径稳定后部署。

完成判定：Chart 和 SDK 未硬编码默认 cluster.local；引入 DNS 缓存前后效果有实测依据。

本节行为核对：[K07](../../reference/official-sources.md#k07)。

## 02.03 建立 MetalLB 主负载均衡与 VIP 规则

### 02.03.01 部署 MetalLB L2 主方案

实施内容：从 .201–.220 预留池中先启用 .201–.210，保留其他地址给不重叠的对比实验。

过程安排：配置地址分配和 L2 宣告范围；确认候选节点位于真实二层网络，VIP 不需要在每台节点固定绑定。

完成判定：VIP 只由负责控制器管理，不与 DHCP、kube-vip .100 或其他实验池重叠。

### 02.03.02 验证地址漂移与入口故障

实施内容：让持续请求通过测试 VIP，停止当前宣告节点上的相关服务或进行受控节点维护。

过程安排：观察 ARP 更新、重新选举、连接中断和恢复；分别记录新连接与已有连接，不承诺完全无感切换。

完成判定：故障后能够恢复访问，切换耗时与遗留连接表现被记录。

### 02.03.03 建立地址使用与撤销流程

实施内容：记录每个 LoadBalancer 的应用、负责人、IP、端口和生命周期。

过程安排：通过销毁测试服务观察地址回收；为关键网关固定声明身份或预留地址，避免 DNS 指向已转给其他应用的 VIP。

完成判定：地址台账与实际 Service 一致，没有失去归属的对外入口。

## 02.04 建立 Gateway API 与传统 Ingress 对照

### 02.04.01 锁定 Gateway API 与实现兼容性

实施内容：检查选定 CRD 版本和 Envoy Gateway 的支持报告，逐一确认 HTTP、gRPC、TCP、UDP 所需能力。

过程安排：只安装实现支持的 API Channel；路由类型稳定性与控制器功能支持分别记录。

完成判定：不会因 CRD 可创建就宣布对应路由已经可工作。

### 02.04.02 部署 Envoy Gateway 与统一入口

实施内容：为网关创建明确的 GatewayClass、Gateway、监听器和受控 LoadBalancer，主入口建议使用 192.168.9.201。

过程安排：跨两台以上可用 Worker 分布数据面，配置 Readiness、资源与节点故障域；控制面和数据面职责分开观察。

完成判定：单个网关 Pod 失效不导致所有入口永久中断；入口仅开放批准的监听端口。

### 02.04.03 配置内部 HTTP 与 HTTPS 路由

实施内容：将测试应用发布为 demo.apps.egon.local，设置 Host、Path、重定向、超时和必要的后端 TLS。

过程安排：通过内部 DNS 和 CA 访问；区分外部终止 TLS 与网关到后端重新加密，不默认认为整条链路都已加密。

完成判定：不同主机和路径命中正确服务，证书链、SAN 与请求主机一致。

### 02.04.04 配置跨命名空间路由与授权

实施内容：为平台统一网关和应用命名空间建立路由绑定策略，测试必要的 ReferenceGrant。

过程安排：明确哪些团队可绑定监听器、引用证书或后端，拒绝未授权跨空间引用。

完成判定：业务团队不能借用其他团队的证书、后端或公开入口。

### 02.04.05 配置 gRPC、TCP 与 UDP 实验

实施内容：根据控制器支持情况分别建立路由，为数据库和消息协议使用专用测试实例。

过程安排：核对协议、TLS 模式、健康检查与客户端连接模型；Kafka 等协议的地址发现问题单独验证，不能只代理一个端口就假定完整集群可用。

完成判定：每种协议完成真实客户端调用；管理和数据中间件不因此默认暴露公网。

### 02.04.06 部署传统 Ingress 对比

实施内容：使用仍维护的控制器和独立 IngressClass，例如经核对的 Traefik，完成 Host、Path 与 TLS 的兼容实验。

过程安排：使用独立测试入口，不与 Envoy Gateway 抢同一对象；不把退役的社区 ingress-nginx 作为新主线。

完成判定：能够用同一应用比较 Ingress 和 Gateway API；清理后保留单一主入口体系。

### 02.04.07 验证流量权重与发布接口

实施内容：让两个版本通过不同后端提供可区分响应，测试网关支持的权重或规则分流。

过程安排：先收集请求分布与错误，不接入自动发布；将已验证的流量控制方式交给 Phase 04 的 Argo Rollouts。

完成判定：灰度路径已经实测，未假定所有 Rollouts 与 Gateway 实现之间天然兼容。

本节行为核对：[N03](../../reference/official-sources.md#n03)。

## 02.05 接入证书自动化与公网发布边界

### 02.05.01 部署 cert-manager 与内部签发器

实施内容：连接阶段 00 建立的内部 PKI，使用受限的中间签发能力为 egon.local 签发证书。

过程安排：核对 Issuer/ClusterIssuer 权限、续期和 Secret 管理；根私钥继续离线，不作为普通集群 Secret 保存。

完成判定：内部证书可自动更新，签发范围与管理员权限分离。

### 02.05.02 执行证书轮换和过期故障实验

实施内容：使用短期测试证书验证续期、Secret 更新和网关重新加载。

过程安排：模拟错误 SAN、不完整链和证书到期，从 Mac、语言客户端和网关分别观察现象。

完成判定：轮换后服务恢复且不要求永久关闭 TLS 校验；故障能够定位到证书层。

### 02.05.03 按白名单发布 egon.top 应用

实施内容：只为批准的测试站点建立 demo.apps.egon.top 等公网记录和公有 CA 证书。

过程安排：核实 DNS 验证、NAT/隧道、安全策略和回源；没有公网能力时先记录阻塞，不将 LAN 内访问记成公网验收。

完成判定：真正公网客户端可访问被批准应用，管理服务和内部 egon.local 名称没有被意外公开。

## 02.06 建立网络隔离与出站策略

### 02.06.01 实施 Namespace 默认拒绝策略

实施内容：为实验和业务空间建立默认拒绝，再显式放行 DNS、网关、业务依赖和监控入口。

过程安排：先在测试命名空间演练，逐条验证放行效果；不对系统命名空间一刀切导致控制平面失联。

完成判定：业务只能访问必要服务，DNS 和基础依赖不会因遗漏而出现隐性故障。

### 02.06.02 比较 Kubernetes 与 Cilium 网络策略

实施内容：用相同应用分别验证标准 NetworkPolicy 和需要的 Cilium 扩展策略。

过程安排：记录 L3/L4、FQDN、身份和可选 L7 能力差异；同时检查允许与拒绝样例，避免只测成功路径。

完成判定：能够说明每条策略由谁执行以及受哪些配置限制。

### 02.06.03 验证出站访问与代理绕行

实施内容：测试 Pod 到 registry.egon.local、Ceph 节点和必要互联网目标的路径。

过程安排：观察 SNAT、实际源地址及回程路由；Ceph 和仓库策略按真实可见源配置，不假设外部服务能直接回到 Overlay Pod IP。

完成判定：内部东西向流量不进入 VPN，外部目标按规则放行。

### 02.06.04 实验 Cilium Egress Gateway 联动 OpenWrt

实施内容：在确认当前 Cilium 功能要求后，为指定工作负载选择出口节点和源地址，再连接 OpenWrt 出口策略。

过程安排：明确此方案本身不自动建立 VPN；规划源地址路由、回程、防火墙和节点故障行为，与显式代理方案分开。

完成判定：目标应用确实使用指定出口；VPN 故障时内网服务不中断，出口单点和会话变化被记录。

## 02.07 建立调度约束与物理故障域

### 02.07.01 建立节点角色与物理宿主机标签

实施内容：记录 cp、infra、storage、compute 角色，并使用 lab.egon.top/esxi-host 等自定义标签表示实际物理位置。

过程安排：虚拟机迁移时同步更新标签；不要把同一 ESXi 上多个 Node 的不同 hostname 当作独立物理容错。

完成判定：标签与真实放置一致，后续反亲和和分布约束可用于物理故障实验。

### 02.07.02 验证 NodeSelector 与 Node Affinity

实施内容：比较简单标签匹配、Required 硬约束与 Preferred 软偏好。

过程安排：通过标签变化、目标节点不足与资源不足场景观察 Pending 和调度选择；注意调度后行为与重新调度行为的区别。

完成判定：能够解释无法调度的具体原因，偏好不会被错误理解为强制保障。

### 02.07.03 验证 Taint 与 Toleration

实施内容：对独立测试节点演练 NoSchedule、PreferNoSchedule 和 NoExecute，包括容忍时长。

过程安排：先保证必要系统 DaemonSet 可运行，再阻止普通业务进入 storage 节点；容忍只解除排斥，并不自动吸引调度。

完成判定：Ceph 资源得到保护，业务不会因一个宽泛 toleration 意外落到错误节点。

### 02.07.04 验证 Pod Affinity 与 Anti-Affinity

实施内容：将关联服务按需共置，关键副本按节点或真实 ESXi 标签分散。

过程安排：比较软硬约束和拓扑键，观察节点不足时的 Pending；对数据库三副本优先验证物理隔离而非表面节点隔离。

完成判定：副本位置可解释，规则不会因过度约束让核心服务无法启动。

### 02.07.05 验证 Topology Spread Constraints

实施内容：定义 maxSkew、topologyKey 与容量不足时的调度行为，并与反亲和对比。

过程安排：逐步增加副本、移除一个故障域或填满某节点，记录分布和 Pending 原因。

完成判定：能区分均匀分布与绝对一节点一副本，实际故障域分布符合实验目标。

## 02.08 实施资源配额、QoS 与可用性预算

### 02.08.01 设置 Requests、Limits、LimitRange 与 Quota

实施内容：为应用、构建和实验 Namespace 分别设置 CPU、内存、临时存储和对象数量预算。

过程安排：测试无资源声明、超配和配额耗尽场景；区分调度使用 Request 与运行期 Limit 的作用。

完成判定：业务不会无限占用平台资源，拒绝创建或 Pending 的原因能被开发者理解。

### 02.08.02 比较 Guaranteed、Burstable 与 BestEffort

实施内容：建立三个受控负载组，核对 QoS 分类与资源声明的实际对应。

过程安排：在指定 Worker 制造温和内存压力，观察驱逐、重启、优先级和使用量；不宣称 QoS 单独决定所有驱逐顺序。

完成判定：记录真实压力响应并释放负载；测试未破坏控制平面和 Ceph 节点。

### 02.08.03 验证 CPU 限流和临时存储耗尽

实施内容：分别让应用耗用 CPU 和可丢弃临时空间，比较延迟、限流、DiskPressure 与驱逐。

过程安排：控制测试大小和中止阈值，先检查宿主机与 Datastore 的实际余量。

完成判定：能够区分 Pod 限制、VM 内磁盘与底层存储满的不同故障，不在真实数据盘上填满空间。

### 02.08.04 验证 PriorityClass 与抢占

实施内容：为测试关键服务和批处理建立不同优先级，观察资源不足时调度器行为。

过程安排：限定抢占范围和测试命名空间；不要随意复制系统最高优先级给所有业务。

完成判定：重要任务可优先恢复，但优先级不会被当作额外资源或性能保证。

### 02.08.05 验证 PDB 与节点维护

实施内容：为多副本服务建立 PDB，在有意驱逐和直接节点故障两种场景下比较。

过程安排：先验证 Drain 因预算受阻时的处理，再在隔离实验模拟故障；明确 PDB 主要约束主动驱逐，不保证抵御所有故障。

完成判定：维护流程能保留预期可用副本，不以绕过 PDB 作为默认解决方式。

## 02.09 对比 Cilium 数据面和负载均衡能力

本节在主线稳定并具备回退记录后执行；优先使用临时集群验证再考虑主集群变更。

### 02.09.01 比较 kube-proxy 与 eBPF 替代

实施内容：保留主集群当前转发基线，为 kube-proxy replacement 建立独立兼容验证。

过程安排：检查 Cilium 要求、API 访问、NodePort、网关和现存连接；迁移时避免两套不兼容规则并行残留。

完成判定：切换前后通过同一通信测试集，任何失败都能回到已知配置。

### 02.09.02 比较 Overlay 与 Native Routing

实施内容：先保留 Overlay，再在具备 Pod 路由条件的实验网络验证 Native Routing。

过程安排：核对上游路由、回程、反向路径检查和 MTU，不因同一 LAN 就认定所有 Pod 网段天然可路由。

完成判定：两种模式在相同负载下具有可比结果，路由配置与前提被完整记录。

### 02.09.03 实验 Cilium LB IPAM 与 L2 Announcements

实施内容：使用与 MetalLB 不相交的测试 IP 池与选择器，核对当前 Beta 限制和 kube-proxy replacement 要求。

过程安排：分别检查地址分配、L2 宣告、流量策略与故障切换；没有让两个控制器同时响应同一 VIP。

完成判定：完成与 MetalLB 的可重复对比，再决定是否改变主方案。

### 02.09.04 实验 Cilium BGP Control Plane

实施内容：只有获得可配置 BGP 的上游设备或隔离软件路由器后才启用，不向家庭主网络盲目宣告路由。

过程安排：规划 ASN、邻居、过滤、Pod/VIP 前缀和撤回测试；软件路由器作为实验节点明确标注。

完成判定：路由只在授权范围传播，失联后撤回行为可观察；设备不足时此项标记硬件前置未满足。

本节行为核对：[N01](../../reference/official-sources.md#n01)、[N02](../../reference/official-sources.md#n02)。

## 02.10 实验 Istio 与工作负载身份

本节基础 mTLS 可独立测试；完整 Trace、SLO 和发布联动在 Phase 04、05 完成后回访。

### 02.10.01 部署 Sidecar 模式服务网格

实施内容：使用独立命名空间和测试应用启用 Istio Sidecar，核对与 Cilium 的兼容设置。

过程安排：验证注入、应用启动、探针、终止和旁路流量；比较资源与延迟基准。

完成判定：服务通信正常，网格接入和退出均可重复，未影响未纳入网格的业务。

### 02.10.02 部署 Ambient 模式并按需增加 waypoint

实施内容：在另一组实验应用上测试 ztunnel 的 L4 身份与加密，再为所需 L7 功能添加 waypoint。

过程安排：避免同一应用重复处于两种冲突模式；分别验证有无 waypoint 的实际可观测性和策略能力。

完成判定：能够区分 L4 安全通道与 L7 治理，不因启用 Ambient 就声称全部流量策略已生效。

### 02.10.03 实现 mTLS、授权与流量策略

实施内容：配置最小授权、超时、重试和必要的流量控制，用故障后端验证行为。

过程安排：防止调用链上多层重试叠加放大压力；记录 TLS 身份、拒绝事件及超时预算。

完成判定：未授权服务被拒绝，故障不会因无界重试扩散，正常流量的额外成本可测量。

### 02.10.04 部署 SPIFFE/SPIRE 身份对比

实施内容：用隔离域和工作负载注册规则测试 SVID 签发、续期、信任和撤销。

过程安排：SPIFFE 信任域规划为 egon.local 并核对实现支持；不要将域名解析、Kubernetes RBAC 与工作负载身份视为同一权限体系。

完成判定：服务获得短期身份并可完成授权通信；联合或网格集成只有在完成适配验证后才启用。

### 02.10.05 完成网络清理与阶段交接

实施内容：保留 Cilium、MetalLB、Envoy Gateway、证书和必要网络策略，关闭闲置 Ingress、实验 VIP 和网格注入。

过程安排：将网络路径、VIP、DNS、策略、调度标签和异常记录交给 Phase 03、04；需要回访的实验登记明确前置条件。

完成判定：主线稳定且控制器责任单一，没有悬空公网记录、残留高权限调试入口或冲突路由。
