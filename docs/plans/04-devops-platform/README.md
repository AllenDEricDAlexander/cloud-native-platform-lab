# Phase 04｜双 CI、GitOps、IaC 与开发者平台工程

文档版本：V3.0。状态：未执行。步骤数：55。

建设 GitLab CI 与 Jenkins 两条完整、对等的流水线，统一多语言构建、制品、安全检查和交付，再用 Backstage 与 Crossplane 提供可审计的研发自助服务。

前置条件：Phase 00–03 主线完成；GitLab、Harbor、Nexus、内部 CA、网关和 Ceph PVC 可用。自动 SLO 发布分析在 Phase 05 提供指标后回访。

实施边界：CI 不直接与 GitOps 竞争写同一业务资源。主集群故障时依靠集群外管理入口和受控恢复执行器，不能要求运行在故障集群中的 Jenkins Controller 或 Runner 自我修复。

## 04.01 定义代码、制品和交付契约

### 04.01.01 划分应用、平台和 GitOps 仓库

实施内容：将应用源码、公共 CI 模板、基础设施代码与部署期望状态分离；所有仓库归入统一项目目录或组织空间。

过程安排：定义开发分支、受保护分支、版本标签与审查流程；明确哪些应用允许自动发布 Dev、哪些变更需要审批。

完成判定：源码提交与环境变更可分别审计，流水线不会因互相更新仓库形成无限触发。

### 04.01.02 建立环境隔离与资源预算

实施内容：为 apps-dev、apps-staging、apps-prod-like 和 CI 建立 Namespace、配额、网络和身份。

过程安排：prod-like 是模拟生产而非实际生产承诺；CI 构建限制到受控计算节点，避免侵占 Ceph 与控制平面。

完成判定：不同环境和构建任务不能任意访问彼此密钥，资源上限与实验硬件相符。

### 04.01.03 定义制品标识与发布标准

实施内容：让镜像、原生包、Chart 和测试结果关联 Git 提交、流水线编号、版本及构建器版本。

过程安排：业务发布固定镜像 Digest，区分标签、不可变制品与临时缓存；数据库迁移版本单独记录。

完成判定：任何部署都能追溯来源，重新构建不会悄悄覆盖已验收的生产型制品。

### 04.01.04 定义可复用应用接口

实施内容：所有语言样例统一健康检查、Readiness、优雅退出、结构化日志、Metrics、Trace 和配置注入方式。

过程安排：为 HTTP 服务与消息 Worker 分别制定适当契约；C/Rust CLI 或库同时保留原生制品交付，不强迫所有项目成为 Web 服务。

完成判定：不同语言能够共享平台验收，而不丢失各自真实的构建与运行需求。

## 04.02 建设构建镜像、依赖和缓存

### 04.02.01 制作受控 Builder 镜像

实施内容：为 Java、Rust、C、C++、.NET、Node 和 Python 建立内部构建镜像及小型运行镜像。

过程安排：固定工具链与系统依赖，内置信任链但不写入秘密；为不同语言记录宿主平台、架构和链接依赖。

完成判定：干净 Runner 能直接从 Harbor 获取 Builder，不在每次 Job 临时下载一整套工具链。

### 04.02.02 配置各语言依赖代理

实施内容：让 Maven/Gradle、npm/pnpm、pip/uv/Poetry、NuGet、Cargo、Conan/vcpkg 指向经验证的内网入口。

过程安排：检查锁文件、校验、上游回退和证书；敏感仓库凭据运行时注入，不打入缓存镜像。

完成判定：每种语言都能从空环境恢复固定依赖，构建结果不依赖偶然缓存。

### 04.02.03 部署隔离的 BuildKit 构建能力

实施内容：优先采用经过 Rocky/内核验证的非特权或 rootless BuildKit，规划并发、存储与 Registry Cache。

过程安排：核对用户命名空间、文件系统和安全策略的兼容性；确需特殊权限时使用专用受限节点和例外，不挂载所有节点的运行时 Socket。

完成判定：应用流水线不能通过构建服务任意控制宿主机；构建失败有可诊断日志。

### 04.02.04 划分四类缓存并防止污染

实施内容：分别管理语言依赖缓存、编译中间产物、BuildKit Layer/Registry Cache 和节点镜像缓存。

过程安排：缓存键包含架构、工具链与锁文件信息；可信与不可信分支分开写入，避免凭据或恶意产物污染共享缓存。

完成判定：缓存命中提高效率但不改变正确性；清空缓存后仍可完成构建。

### 04.02.05 验证离线构建与制品保留

实施内容：挑选固定提交和已预热依赖，在限制互联网的干净执行环境构建。

过程安排：统计依赖缺口与实际外网流量；分别处理构建缓存、测试结果和正式制品的保留策略。

完成判定：已声明支持的离线组合全部成功，未缓存新依赖明确报错而非隐式绕过出口政策。

## 04.03 实现 GitLab CI 完整流水线

### 04.03.01 部署 Runner 管理器和 Kubernetes Executor

实施内容：在 ci 命名空间部署 Runner，按受保护分支、构建类型和敏感权限划分标签与执行范围。

过程安排：核对 Runner 管理器、Job Pod 的 ServiceAccount、资源与网络权限；注册材料受控保存并可轮换。

完成判定：任务按需创建 Pod，完成后释放；普通 MR 不会得到平台管理员凭据。

### 04.03.02 建立公共 GitLab CI 模板

实施内容：将检出、格式检查、测试、依赖缓存、构建、制品、扫描和 GitOps 更新设计为可组合模板。

过程安排：由最小测试项目验证 include 关系与触发条件，再让各语言项目引用；模板版本与应用版本独立管理。

完成判定：多个项目共用模板时行为一致，模板变更具有回归和回退方案。

### 04.03.03 实现合并请求和分支流水线

实施内容：区分 MR 验证、开发分支构建、标签发布与正式环境审批。

过程安排：设置依赖关系、失败中止、超时、重试和并发控制；不受信任 MR 仅执行无生产凭据的任务。

完成判定：代码检查失败会阻断发布，重复触发不会并行修改同一环境。

### 04.03.04 实现制品发布与 GitOps 提交

实施内容：将测试通过的镜像、原生制品和元数据提交到对应仓库，然后创建受控的环境变更。

过程安排：使用限定仓库权限的机器人账号；防止 GitOps 回写触发自身，审批后由 Argo CD 执行实际部署。

完成判定：一次提交能追踪到一个可审计版本，流水线不直接用管理员权限修改业务 Deployment。

### 04.03.05 验证 GitLab CI 故障恢复

实施内容：模拟 Runner 重启、构建 Pod 被驱逐、仓库超时、凭据过期和重跑。

过程安排：区分可重试构建与不可重复的外部写操作；通过幂等发布防止重复标签和重复环境资源。

完成判定：失败任务可安全重试，结果与首次触发的提交和制品身份一致。

本节行为核对：[D01](../../reference/official-sources.md#d01)。

## 04.04 实现 Jenkins 完整流水线

### 04.04.01 部署 Jenkins Controller 与持久化

实施内容：将 Jenkins Controller 部署于受控平台空间，使用 Ceph PVC 和 jenkins.k8s.internal.egon.top 的内部 TLS 入口。

过程安排：固定核心与插件版本，限制 Controller 不承担普通构建；保存配置、凭据加密材料和备份。

完成判定：重建 Controller 后能恢复配置与任务，普通用户不能安装任意高权限插件。

### 04.04.02 配置动态 Kubernetes Agent

实施内容：通过 Kubernetes Plugin 为不同语言创建临时 Agent，定义最小权限与节点选择。

过程安排：与 GitLab Runner 共用 Builder 标准但隔离执行身份；限定并发和构建缓存占用，保留关键失败日志。

完成判定：Agent 按任务生成和销毁，不需要长期保留七台独立编译虚拟机。

### 04.04.03 建立 Jenkins Configuration as Code 与共享库

实施内容：将可声明的系统配置、Pipeline 模板和 Shared Library 纳入版本管理。

过程安排：秘密值使用受控注入，不进入配置仓库；固定插件依赖并验证备份恢复后的配置重建。

完成判定：Jenkins 不是只能在管理页面手工重建的单次安装。

### 04.04.04 实现 Multibranch 与标准阶段

实施内容：通过受控 Webhook 或仓库扫描发现分支和 MR，执行与 GitLab CI 对等的质量、构建、安全和发布阶段。

过程安排：验证分支过滤、可信 Jenkinsfile、凭据作用域、审批及超时；不允许任意分支改写高权限 IaC 流水线。

完成判定：同一语言与提交在两套 CI 中得到可比较的制品和测试结果。

### 04.04.05 实现 Jenkins GitOps 发布与失败恢复

实施内容：让 Jenkins 使用同样的环境变更契约更新 GitOps 仓库，测试 Agent 丢失与 Controller 重启。

过程安排：把重试放在幂等阶段，对已发布制品使用身份检查；备份恢复测试在临时实例完成。

完成判定：任务重跑不重复部署不一致版本，Controller 数据丢失后有明确恢复路径。

本节行为核对：[D02](../../reference/official-sources.md#d02)。

## 04.05 完成七类语言的双流水线适配

### 04.05.01 完成 Java 与 Spring Boot 服务

实施内容：实现 JDK 21 主线及 JDK 25 对比，覆盖 Maven/Gradle、JUnit、集成测试、打包和容器化。

过程安排：核对 Spring Boot 与工具链兼容性；测试容器内存、优雅关闭、数据库连接池和 Java CA 信任，再分别由两套 CI 构建。

完成判定：Java 服务在 K8s 可健康运行、追踪和回滚，两套 CI 都有可重复的成功记录。

### 04.05.02 完成 Rust 服务与原生制品

实施内容：实现格式、Clippy、测试、Cargo 锁文件、release 构建与镜像发布。

过程安排：比较目标平台、glibc/musl、动态依赖和运行镜像证书；不假定一次交叉编译即可在所有 Linux 上运行。

完成判定：Rust API 或 Worker 可部署，同时可以分发对应平台的原生程序，双 CI 结果可核验。

### 04.05.03 完成 C 服务或计算 Worker

实施内容：使用 GCC/Clang、CMake 和 CTest 构建带测试输入输出的程序。

过程安排：检查警告、链接库、内存问题检查和运行时依赖；制品与容器分别归档并在实际目标环境执行。

完成判定：不是只生成一个二进制文件，而是完成可运行、可验证、可回滚的交付链。

### 04.05.04 完成 C++ 服务与依赖缓存

实施内容：覆盖 GCC/Clang、CMake/Ninja、Conan/vcpkg 与单元/集成测试，选择 gRPC 或计算服务样例。

过程安排：记录 ABI、标准库、编译选项和缓存键；分别测试冷缓存与热缓存，避免跨工具链复用不兼容库。

完成判定：双 CI 构建结果可在目标运行镜像执行，依赖和原生制品具有准确版本。

### 04.05.05 完成 C# 与现代 .NET 服务

实施内容：使用匹配版本的 .NET SDK、NuGet、单元测试和 ASP.NET Core 服务。

过程安排：比较框架依赖与自包含发布、容器证书和配置；Windows-only .NET Framework/MSVC 需求登记为额外 Windows Runner 实验。

完成判定：Linux 支持范围与 Windows 需求清楚，现代 .NET 服务完成两套 CI/CD。

### 04.05.06 完成 JS/TS 前后端交付

实施内容：覆盖 Node、npm/pnpm、锁文件、类型检查、测试和生产构建。

过程安排：区分 Node 服务运行与静态前端托管；检查构建时配置与运行期配置、Source Map 和依赖安装安全。

完成判定：JS/TS 项目可由双 CI 发布，环境切换不会把秘密写入前端静态包。

### 04.05.07 完成 Python 服务和任务程序

实施内容：覆盖 uv/pip/Poetry 的选定主线、锁文件、Ruff、pytest、Wheel 与 FastAPI 或 Worker。

过程安排：区分纯 Python 与带原生扩展依赖，验证基础系统包、CA 信任和多进程资源；分别测试双 CI。

完成判定：Python 制品与镜像可重现，运行环境没有依赖开发机本地路径。

### 04.05.08 执行十四种构建发布组合验收

实施内容：对七类语言分别执行 GitLab CI 与 Jenkins，使用固定提交、相同依赖和同一验收应用接口。

过程安排：记录构建耗时、缓存命中、峰值资源、制品校验及发布结果；失败组合修复后重测，不以一种语言代表全部。

完成判定：至少十四个语言与 CI 组合有完整记录，并形成公共模板的回归集。

## 04.06 通过两套 CI 实施 IaC

### 04.06.01 划定 OpenTofu、Ansible 与 GitOps 管理范围

实施内容：OpenTofu 管虚拟机和虚拟硬件，Ansible 管主机基线与 kubeadm/cephadm，GitOps 管集群资源。

过程安排：核对 vCenter/ESXi 许可证、API 写入权限和 Provider 支持；先验证可创建销毁的小型 VM，不凭界面权限推断 API 能力。

完成判定：每层工具的实际可操作范围被验证，同一对象只有一个主状态来源。

### 04.06.02 建立远端 State、锁和备份

实施内容：优先使用集群外且支持状态锁的后端，例如经过验证的 GitLab HTTP State。

过程安排：从初始本地状态受控迁移，验证锁、权限、加密、历史和备份；状态文件可能包含敏感数据，不提交普通 Git。

完成判定：两套 CI 同时请求变更时能互斥，后端故障不会导致随意新建另一份状态。

### 04.06.03 实现 GitLab CI 的 IaC 流程

实施内容：定义验证、格式检查、Plan、人工审批、Apply、主机初始化和验证阶段。

过程安排：先在临时资源范围执行创建、扩容与回收，再推广到批准对象；高风险删除单独审批。

完成判定：GitLab CI 能复现一台合格实验 VM，并保留变更前后状态与验证记录。

### 04.06.04 实现 Jenkins 的 IaC 流程

实施内容：使用同一模块和约定实现 Jenkins 版本，保持审批、锁、计划比对和凭据边界等价。

过程安排：与 GitLab CI 交替操作同一受控测试状态，检查未发生配置漂移和并发 Apply；不同时启动两个写入者。

完成判定：Jenkins 并非简化演示，具备与 GitLab CI 对等的基础设施创建、变更与回收能力。

### 04.06.05 实现 Ansible 幂等、分批和漂移修复

实施内容：将 OS、容器运行时、网络和节点角色配置纳入可重复任务，敏感数据通过受控接口取得。

过程安排：先执行检查与差异评估，再单节点、分批应用；对 Ceph 和控制平面使用专属维护顺序。

完成判定：重复执行不会抹掉运行身份与数据，变更失败可隔离在当前批次。

### 04.06.06 建立集群外恢复执行器

实施内容：为主集群不可用时保留管理 VM，以及只运行受信任基础设施任务的外部执行通道。

过程安排：外部 GitLab Runner 或人工批准的管理执行器仅接受受保护流程，不承担不可信源码编译；Jenkins 故障不阻塞此通道。

完成判定：能够在 K8s Runner 与 Jenkins 都停止时获取仓库和恢复材料并执行重建。

### 04.06.07 验证 IaC 失败补偿与销毁保护

实施内容：模拟创建部分成功、初始化失败和状态后端短暂不可用。

过程安排：检查资源实际状态、处理导入或补偿，禁止把重新 Apply 或 Destroy 当万能事务回滚。

完成判定：对正式数据盘、Ceph 和基础仓库设置保护；销毁实验只覆盖明确允许的临时资源。

## 04.07 建设 Helm、Kustomize 和 Argo CD

### 04.07.01 制作 Helm Chart 与多环境覆盖

实施内容：为样例服务建立 Chart，明确 Values 契约、探针、资源、Service、Gateway 和 Secret 引用。

过程安排：使用 Kustomize 对比 Base/Overlay；验证渲染、依赖、Hook、升级与回退，避免 Helm 和 Kustomize 同时修改同一字段产生歧义。

完成判定：同一应用能够在 Dev、Staging、Prod-like 复用模板而不复制大量不可维护文件。

### 04.07.02 部署 Argo CD 与最小权限项目

实施内容：通过 argocd.k8s.internal.egon.top 内网入口、受限仓库凭据和 AppProject 管理目标命名空间与资源类型。

过程安排：先导入非关键应用，验证同步、漂移、健康判定与审查；对基础系统和有状态资源谨慎启用自动 Prune。

完成判定：GitOps 只能管理授权范围，错误提交不会立即级联删除全部存储。

### 04.07.03 建立分层同步和依赖顺序

实施内容：安排 Namespace、CRD、Operator、CR 和应用之间的同步顺序与健康判定。

过程安排：解决刚创建 CRD 尚未可用和 Operator 尚未 Ready 的阶段差异；首次手工引导后再受控纳入 GitOps。

完成判定：集群从空白状态恢复时不会因为对象顺序而持续失败，也没有自举环路。

### 04.07.04 验证 HPA 与 GitOps 字段所有权

实施内容：明确副本数由 HPA 管理，应用模板和 GitOps 的差异处理按实际行为配置。

过程安排：在持续同步和压力变化下观察 replicas，避免 GitOps 不停拉回手工固定值；记录忽略字段的范围。

完成判定：自动扩缩容与声明式交付不发生反复抢写，其他配置漂移仍可被检测。

### 04.07.05 建立 ApplicationSet 与通知

实施内容：使用受控生成器批量管理环境应用，增加部署结果、失败和审批提示。

过程安排：验证生成源变化、应用删除和重建行为；避免一个列表误删导致大量应用被清空。

完成判定：批量部署与通知可用，删除范围可预览且可审核。

本节行为核对：[D06](../../reference/official-sources.md#d06)。

## 04.08 实现渐进式发布和供应链安全

### 04.08.01 部署 Argo Rollouts 并验证路由适配

实施内容：选择与当前 Gateway/网格实际兼容的流量管理接口或维护中的适配器。

过程安排：先发布双版本测试服务，确认流量权重能被真实改变；适配不支持时记录并使用已验证入口方案，不伪造集成。

完成判定：Rollout 状态与客户端实际流量一致，版本切换不是只改变副本数量。

### 04.08.02 实现 Canary 与 Blue/Green

实施内容：定义预览、分批权重、暂停、人工批准、最终切换和回退策略。

过程安排：使用持续请求验证两个版本的流量和数据兼容；数据库结构变更采用前后兼容方式。

完成判定：可以按流量而非猜测决定发布时间，回退应用不会破坏数据库结构。

### 04.08.03 接入发布分析与自动中止

实施内容：在 Phase 05 指标可用后，为延迟、错误率和业务成功率建立 AnalysisRun 判定。

过程安排：验证指标无数据、监控不可用和坏版本三种情况；无数据不能被默认当作健康通过。

完成判定：自动中止与回退具有明确阈值和实测依据，发布失败可解释。

### 04.08.04 建立 SBOM、扫描和来源证明

实施内容：构建过程中生成 SBOM、漏洞结果与适用的构建来源元数据，关联制品 Digest。

过程安排：从宽松报告开始建立策略，再增加阻断；明确这些步骤不自动等于达到某个完整 SLSA 等级。

完成判定：发布审查可以查看来源、依赖和扫描时间，离线扫描注明数据库新鲜度。

### 04.08.05 使用 Cosign 签名并保留可信材料

实施内容：选择与内网离线目标相容的密钥或身份签名方式，限制签名凭据只用于可信发布。

过程安排：验证 Harbor 保存相关制品、签名可被检索及离线验证所需材料；Keyless 所依赖的外部服务不能被忽略。

完成判定：可验证已发布镜像来源，签名私钥不进入 Builder 镜像或不可信 MR。

### 04.08.06 接入准入校验与拒绝发布实验

实施内容：由 Kyverno 或选定策略验证镜像来源、Digest、签名及必要资源声明。

过程安排：先 Audit 再逐步 Enforce，准备可信与不可信镜像测试；缓存和仓库不可用时的策略行为需单独核对。

完成判定：非法镜像确实被拒绝，关键恢复组件保留受控而非无限制的应急通道。

本节行为核对：[D07](../../reference/official-sources.md#d07)、[A05](../../reference/official-sources.md#a05)。

## 04.09 建设 Backstage 与 Crossplane 平台入口

### 04.09.01 部署 Backstage 并建立服务目录

实施内容：使用 backstage.k8s.internal.egon.top 建立目录，登记负责人、系统、应用、API、仓库与文档。

过程安排：配置受限仓库集成和身份入口；先使用少量服务验证目录同步，再导入全部语言样例。

完成判定：开发者可以找到服务及其责任人，不只是打开一个空门户。

### 04.09.02 实现 Software Templates 与双 CI 选择

实施内容：为七类语言设计模板参数，允许选择 GitLab CI 或 Jenkins、环境、资源和数据依赖。

过程安排：生成源码骨架、流水线、部署模板、文档与目录项；模板动作使用最小凭据，重复提交具备冲突处理。

完成判定：选定模板能够建立一个真实可构建仓库，错误参数被清晰拒绝。

### 04.09.03 部署 Crossplane 与版本化平台 API

实施内容：建立 DevApplication、DevDatabase 等自定义 API，定义 schema、组合资源和版本策略。

过程安排：核对所选 Crossplane v2 的作用域与 Provider/Function 能力；没有支持的外部资源不强行承诺自动创建。

完成判定：平台 API 可创建、验证和观察，字段对应明确的资源交付行为。

### 04.09.04 划分 Argo CD、Crossplane 与 Operator 所有权

实施内容：由 Argo CD 管理顶层平台请求，Crossplane 管理组合资源，数据库 Operator 管理自身子资源。

过程安排：检查资源树、Finalizer、状态与字段经理；禁止 Argo CD 同时发布 Crossplane 生成的同名 Deployment/PVC。

完成判定：持续调谐不会产生控制器冲突，删除申请后的数据保留规则明确。

### 04.09.05 完成开发者自助服务端到端交付

实施内容：以 Rust API 加 PostgreSQL 为完整样例，分别选择 GitLab CI 与 Jenkins。

过程安排：从门户创建仓库到 CI 构建、镜像签名、GitOps 交付、数据库就绪、应用健康逐层观察，并测试一步失败后的重试。

完成判定：开发者可看到资源申请和发布结果，失败不遗留无人管理的数据库或公网入口。

### 04.09.06 完善 TechDocs、API 目录与权限

实施内容：将七阶段文档和服务文档接入开发者文档入口，展示运行、构建和部署状态。

过程安排：接入 Keycloak/OIDC 的完整统一身份在 Phase 06 回访；当前保留授权范围和本地恢复入口。

完成判定：门户不是绕过平台权限的超级管理员，文档与版本能够对应。

本节行为核对：[D04](../../reference/official-sources.md#d04)、[D05](../../reference/official-sources.md#d05)。

## 04.10 开展 Tekton、Flux 与镜像分发对照

### 04.10.01 实验 Tekton 原生流水线

实施内容：用 Task、Pipeline 和对应运行对象复现一个语言样例的测试、构建和发布。

过程安排：复用 Builder、Harbor、缓存和制品标准，但使用独立身份与对象；按需增加 Results 或供应链相关能力。

完成判定：能够比较 Kubernetes 原生任务编排与 GitLab/Jenkins 的执行和维护差异。

### 04.10.02 实验 Flux GitOps

实施内容：在独立命名空间或第二集群用 Flux 管理一组测试应用，验证源码同步、渲染和收敛。

过程安排：同一对象不同时归 Argo CD 和 Flux 管理；执行受控漂移、回退与清理。

完成判定：得到真实 GitOps 对照记录，主 Argo CD 配置保持稳定。

### 04.10.03 实验 Dragonfly P2P 分发

实施内容：部署适合当前规模的 Dragonfly 模式，核对与 containerd、Harbor 路径和证书的集成。

过程安排：比较单节点、十节点并发、首次与重复下载；记录上游流量、仓库流量和节点互传量。

完成判定：分发方案节省何处流量有测量依据；故障时有回退到 Harbor 的可控路径。

### 04.10.04 完成 Phase 04 交接与清理

实施内容：保留主 CI/CD、必要 Builder 与平台 API；按资源策略停用 Tekton、Flux、Dragonfly 等非当前实验。

过程安排：归档十四种构建组合、双 IaC、Backstage 自助、签名和发布记录，向 Phase 05 提供统一遥测契约。

完成判定：应用交付可重复、权限可审计，实验对照组件没有遗留互相竞争的控制器。
