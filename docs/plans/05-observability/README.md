# Phase 05｜可观测性、日志、性能、SLO 与成本治理

## 05.01 建立遥测契约和容量计划

[本专题具体操作、配置与检查](implementation-details.md#05-01)

### 05.01.01 定义服务、环境和版本标识

实施内容：为七类语言定义一致的服务名称、环境、版本、实例、请求关联和业务错误分类。

过程安排：核对选定 OpenTelemetry 版本的语义约定；同一字段从应用、Collector 到后端保持一致，不各自随意命名。

完成判定：一个应用的指标、日志和 Trace 能通过稳定标识关联。

### 05.01.02 确定保留、采样和成本预算

实施内容：分别规划 Metrics、Logs、Traces、Profiles 的采集频率、保留时间和容量上限。

过程安排：按实际每天写入量和 Ceph 副本开销评估，不将对象存储标称空间全部用于观测；先短保留再扩大。

完成判定：具有可执行的容量预算和超限处理方法，不等磁盘满才临时删数据。

### 05.01.03 建立遥测隐私与访问边界

实施内容：制定日志脱敏、个人信息、密码、Token、请求体和数据库查询内容的采集限制。

过程安排：先在样例中产生可识别测试秘密，验证采集链会过滤或遮盖；按团队和用途控制查询权限。

完成判定：日志和 Trace 不成为新的凭据泄漏渠道，调试级采集有明确期限。

### 05.01.04 部署集群外可达性探测

实施内容：在管理 VM 或独立设备保留 DNS、API、Harbor、Ceph 与关键站点的轻量探测。

过程安排：探测结果和最低限度告警不依赖被监控的 K8s/Ceph；验证主集群停止时仍能记录故障。

完成判定：不会因整个观测平台与业务同时下线而误以为没有故障。

## 05.02 建设 Prometheus、Grafana 与 Alertmanager

[本专题具体操作、配置与检查](implementation-details.md#05-02)

### 05.02.01 部署指标平台与持久化

实施内容：选择匹配版本的 Prometheus Operator 方案，安装 Prometheus、Grafana 与 Alertmanager。

过程安排：定义副本、资源、存储、保留与访问权限；先低资源运行，不把默认 Chart 的全套配置原样塞入实验集群。

完成判定：平台可采集和查询，初始资源使用落在预算内。

### 05.02.02 采集 Kubernetes 与节点状态

实施内容：接入 kube-state-metrics、node-exporter、kubelet 指标和适用的控制平面指标。

过程安排：核对认证、TLS、端点可达性和抓取范围；避免为取指标将 etcd 或控制平面监听接口开放到公网。

完成判定：可观察节点、Pod、调度、重启、资源和控制面状态，抓取失败本身也被发现。

### 05.02.03 建立 ServiceMonitor、PodMonitor 与规则

实施内容：为样例应用和 Operator 管理的服务建立可审计的采集对象与 Recording Rules。

过程安排：核对 Label Selector、命名空间范围和目标健康，限制不可信应用生成无限新指标。

完成判定：目标能按规范接入，错误选择器不会悄悄让服务失去监控。

### 05.02.04 建立 Grafana 数据源和基础面板

实施内容：通过 grafana.k8s.internal.egon.top 内网入口配置 Prometheus 等受控数据源，建立集群、节点、Namespace、应用与构建的分层面板。

过程安排：面板和告警定义纳入 Git，必要的凭据通过受控 Secret 注入；记录单位与聚合口径。

完成判定：重建 Grafana 后可恢复面板，不依赖唯一管理员浏览器中的临时设置。

### 05.02.05 建立 Alertmanager 分组与路由

实施内容：按严重性、服务和责任团队规划分组、去重、抑制、静默与恢复通知。

过程安排：使用已有可用的通知渠道验证告警发送，不预设第三方账号已接入；模拟风暴验证抑制。

完成判定：故障能通知到责任方，恢复消息可关联原事件，测试告警不会无止境发送。

### 05.02.06 验证观测组件自身故障

实施内容：模拟抓取端点超时、Prometheus 重启、Alertmanager 不可用和 Grafana 数据源失败。

过程安排：区别无数据、零值与健康状态；观测链的失效也需要记录与独立探测。

完成判定：看板空白不被误判为业务没有问题，平台自身恢复路径明确。

## 05.03 覆盖 Ceph、基础设施和中间件监控

[本专题具体操作、配置与检查](implementation-details.md#05-03)

### 05.03.01 接入 Ceph 指标和容量告警

实施内容：观察 MON 多数派、OSD、PG、慢请求、容量、恢复流量和客户端延迟。

过程安排：把 Ceph 逻辑容量与底层 Datastore 实际剩余空间并列展示，避免只监控上层池容量。

完成判定：可以识别副本恢复与底层磁盘风险，对三故障域降级状态有明确告警。

### 05.03.02 接入 ESXi、Rocky 与网络设备

实施内容：选择与实际权限兼容的指标采集方式，记录 VM CPU、内存、Datastore、网卡和主机状态。

过程安排：不假定所有 ESXi 版本/许可支持相同接口；网络设备缺少管理能力时记录可测范围，不编造交换机端口指标。

完成判定：能够区分物理宿主机瓶颈、VM 资源不足和容器内限制。

### 05.03.03 接入 PostgreSQL 与 Redis

实施内容：采集数据库连接、事务、复制、查询、缓存命中、淘汰和持久化健康。

过程安排：使用只读监控账户或 Operator 支持接口；敏感查询内容和高成本采集按需开启。

完成判定：故障切换、连接耗尽与缓存压力可以被观察，监控不会成为显著业务负担。

### 05.03.04 接入 Kafka、RabbitMQ 与 NATS

实施内容：重点监控 ISR、Broker、Consumer Lag、队列积压、确认失败与持久存储状态。

过程安排：用已知数量消息和受控消费者暂停验证指标变化，核对指标单位与聚合维度。

完成判定：数据能直接用于后续 KEDA 和业务 SLO，而不是只有进程存活指标。

### 05.03.05 接入 GitLab、Jenkins、Harbor 与 Nexus

实施内容：观测构建队列、Job 失败、Agent/Runner、仓库容量、请求耗时和缓存命中。

过程安排：将 Job、提交、制品版本与监控事件关联，区分外部下载慢、依赖仓库慢和编译器耗时。

完成判定：能够定位流水线慢在哪一层，为两套 CI 性能比较提供依据。

## 05.04 建立 OpenTelemetry 统一入口

[本专题具体操作、配置与检查](implementation-details.md#05-04)

### 05.04.01 部署 Collector 采集与汇聚层

实施内容：按实际需要划分节点 Agent 和集群 Gateway Collector，配置接收、批处理、队列、内存限制和导出。

过程安排：避免同一个进程对所有信号承担无界缓冲；核对 TLS、认证和多租户隔离，入口只对授权应用开放。

完成判定：Collector 在后端短暂不可用时行为可预测，过载不会拖垮节点。

### 05.04.02 接入多语言 SDK 与自动插桩

实施内容：Java、.NET、Node、Python 优先验证可用自动插桩，Rust、C/C++ 采用匹配 SDK 或明确的手动埋点。

过程安排：逐语言测试版本兼容、请求上下文、资源属性和导出；不保证所有语言具有相同自动插桩或 Profiling 能力。

完成判定：七类语言至少有可用的统一遥测路径，能力缺口有明确适配方案。

### 05.04.03 贯通同步和异步上下文

实施内容：用 Java/Rust/Python 或其他样例建立 HTTP/gRPC 调用链，再通过 Kafka/RabbitMQ 传递上下文。

过程安排：区分同步父子关系和异步链接，检查重试、批处理和消费者并发中的 Trace 关联。

完成判定：可以追踪一项业务从请求到消息处理的过程，异步阶段没有被错误拼成一条不真实同步链。

### 05.04.04 控制采样、高基数与重传

实施内容：根据业务错误和关键路径制定采样，限制 URL、用户 ID、消息 ID 等高基数标签。

过程安排：比较头采样和尾采样的资源成本，测试 Collector 队列满、丢弃与重试；记录可接受的数据缺失。

完成判定：遥测量受控，后端故障不会通过无限重传放大为业务故障。

本节行为核对：[O01](../../reference/official-sources.md#o01)。

## 05.05 实现 ELK 日志平台

[本专题具体操作、配置与检查](implementation-details.md#05-05)

### 05.05.01 部署 ECK 与小规模 Elasticsearch

实施内容：使用经核对版本的 ECK 管理 Elasticsearch、Kibana 和适用的 Logstash 能力。

过程安排：检查许可证与功能边界，规划索引副本、存储和内存；先低写入规模，不同时开启最大化 Kafka/CI 压力。

完成判定：ELK 在资源预算内稳定运行，部署方式不依赖未经确认的商业功能。

### 05.05.02 部署 Fluent Bit 节点日志采集

实施内容：通过 DaemonSet 采集 CRI 日志，补充 Kubernetes 元数据并控制主机目录访问。

过程安排：处理多行异常、日志轮转、节点重启和容器删除；offset 与缓冲位置可持久保留且不写满系统盘。

完成判定：重启后日志不大量丢失或重复，Agent 权限仅覆盖必要日志。

### 05.05.03 建立 Logstash 解析与缓冲链路

实施内容：让需要复杂解析、字段转换和清洗的日志经过 Logstash，普通链路可保留直接写入对照。

过程安排：验证结构化 JSON、非结构化消息、异常栈、解析失败和队列积压；保留失败样本但脱敏。

完成判定：能定位日志在哪一段失败，解析规则变更可以回退。

### 05.05.04 建立索引模板与生命周期

实施内容：定义数据流或索引模板、字段映射、保留和清理，避免动态字段无限增长。

过程安排：用受控数据测试索引膨胀、字段类型冲突、查询与生命周期回收；不将关键业务字段随意设为高成本全文索引。

完成判定：写入和查询可用，存储增长具有边界。

### 05.05.05 建立 Kibana 查询与故障案例

实施内容：创建按服务、环境、版本、Trace ID 和错误分类的检索视图。

过程安排：用数据库失败、发布失败和权限拒绝样例验证定位过程，查询模板与调查记录归档。

完成判定：可从具体故障快速找到相关日志，而不是只看到一屏实时滚动信息。

本节行为核对：[O02](../../reference/official-sources.md#o02)。

## 05.06 实现 Loki、Tempo 与 Pyroscope

[本专题具体操作、配置与检查](implementation-details.md#05-06)

### 05.06.01 部署 Loki 并规划对象存储

实施内容：在资源许可下建立 Loki 路线，使用 Ceph RGW 的独立 Bucket、受限凭据和保留策略。

过程安排：通过 Fluent Bit、OTel Collector 或受支持的 Alloy 路线导入选定日志；不引入已停止维护的 Promtail 作为新基线。

完成判定：能够用 Grafana 检索日志，数据存储与凭据不和其他系统混用。

### 05.06.02 控制 Loki 标签与查询模式

实施内容：只将稳定低基数字段作为标签，对 Trace ID、用户或请求级信息采用合适的内容/元数据方式。

过程安排：使用与 ELK 相同的日志样本、保留和查询场景比较；避免两套系统无条件长期重复写全量。

完成判定：两种后端的查询能力与资源差异有可比实验数据。

### 05.06.03 部署 Tempo 并关联日志与指标

实施内容：通过 OTLP 接收追踪，配置受控存储、保留与 Grafana 关联跳转。

过程安排：验证 Trace ID 从日志到 Trace 的跳转、跨语言链路和缺失 Span；为服务拓扑和相关指标核对生成来源。

完成判定：一项业务异常能够关联到具体调用阶段，不依赖人工猜测链路。

### 05.06.04 接入 Pyroscope 持续性能剖析

实施内容：优先在兼容的 Java 等样例上采集 CPU 或内存剖析，再扩展支持的其他语言。

过程安排：核对 Agent、采样开销和符号信息；在同一负载下比较启用前后延迟与资源，不假定 C/Rust/.NET 接入方式完全相同。

完成判定：能够找到实际热点，并清楚标注当前已支持的语言和性能开销。

### 05.06.05 验证对象存储与观测后端中断

实施内容：模拟 RGW 凭据过期、网络延迟和后端重启，观察日志与追踪的缓冲、丢弃和恢复。

过程安排：限制故障范围，记录 Collector、Agent、后端的背压与内存；Ceph 全故障由集群外探测补充。

完成判定：遥测失效不会无界消耗业务资源，数据缺口能被解释。

## 05.07 建立 SLI、SLO 与发布分析

[本专题具体操作、配置与检查](implementation-details.md#05-07)

### 05.07.01 为参考业务定义 SLI 与 SLO

实施内容：选择真实用户成功率、请求延迟和消息处理时效，不只以 Pod Ready 作为服务可用性。

过程安排：说明分母、排除项、时间窗口和数据源；先测基线再设目标，不预先声称达到固定百分比。

完成判定：目标具有可计算定义，不因监控无数据而虚增可用性。

### 05.07.02 建立错误预算和燃尽告警

实施内容：按 SLO 计算错误预算，配置多窗口告警和责任处置。

过程安排：用短时高错误与持续低错误两种样例验证触发行为，避免单阈值在低流量下频繁误报。

完成判定：告警能区分紧急故障与趋势风险，恢复后错误预算记录仍可追踪。

### 05.07.03 将指标接入 Argo Rollouts

实施内容：回访 Phase 04 的发布分析接口，将已验证的成功率、延迟和关键业务指标作为判据。

过程安排：发布故意退化版本，测试暂停、人工批准、自动中止以及监控不可用情形。

完成判定：坏版本的发布能够被实际指标阻断，自动回退结果经过客户端验证。

### 05.07.04 建立统一故障时间线

实施内容：将部署、配置变更、节点维护、Ceph 恢复和业务告警关联到统一事件记录。

过程安排：统一时间显示与时区，底层时间保持同步；记录检测、响应、恢复和数据校验四个节点。

完成判定：后续容灾实验可以计算真实恢复过程，而非仅用第一条告警到最后一条日志估算。

本节行为核对：[D07](../../reference/official-sources.md#d07)。

## 05.08 开展压测、容量和成本实验

[本专题具体操作、配置与检查](implementation-details.md#05-08)

### 05.08.01 建立 k6/Locust 压测基准

实施内容：选定可重放的数据、并发模型、持续时间和停止阈值，客户端资源单独观测。

过程安排：先确认压测端不是瓶颈，控制预热与缓存状态；测试只针对授权的实验服务。

完成判定：性能数据可复现，压测不会误伤家庭网关或公开第三方目标。

### 05.08.02 比较七类语言的运行表现

实施内容：对相近业务逻辑比较启动时间、吞吐、延迟、内存和 CPU，不把不同业务直接排名。

过程安排：固定节点资源、数据、请求与依赖，记录 JIT 预热、编译参数、运行时版本和 GC 差异。

完成判定：结果注明实验条件和局限，不将一次家庭实验概括为语言普遍优劣。

### 05.08.03 比较双 CI 和镜像缓存效率

实施内容：对相同提交测试 GitLab/Jenkins 的冷缓存、暖缓存和受控并发。

过程安排：记录排队、拉镜像、下载依赖、编译、测试和推送各阶段；必要时回访 Dragonfly 分发测试。

完成判定：能够判断瓶颈在 CI 编排、网络、仓库还是编译，不仅比较总耗时。

### 05.08.04 评估 Ceph 与应用的共享瓶颈

实施内容：在数据库、消息、ELK 和构建任务间逐步增加并发，观察 Ceph、Datastore、VM 和网络。

过程安排：一次只改变一个关键因素，达到安全阈值即停止；结果区分 RAID VMDK 功能实验与真实独立磁盘性能。

完成判定：得到当前硬件可以承受的工作负载组合及并发上限建议。

### 05.08.05 部署 OpenCost 与自建成本模型

实施内容：配置自建环境的 CPU、内存、存储和可选电力/折旧单价，用于相对成本和资源浪费分析。

过程安排：说明分配成本、空闲成本和共享组件分摊；费用是模型估算，不等于真实账单或实际电表读数。

完成判定：可以按团队、环境和应用比较资源占用，估算假设透明。

### 05.08.06 分析 Requests、实际用量与效率

实施内容：比较预留、限制、实际使用和任务耗时，给出调整副本与资源申请的依据。

过程安排：先建议再验证，避免直接让成本优化工具缩减数据库和控制平面关键资源。

完成判定：优化后性能与可靠性未明显退化，节约量有数据支撑。
