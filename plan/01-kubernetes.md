## 01.01 核验节点与运行时

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-01)

### 01.01.01 复核十节点的基础状态

实施内容：核对主机身份、DNS、时间、网关、磁盘、CPU 指令和镜像仓库信任，验证跨宿主机节点互通。

过程安排：先处理 cp01 与一个 Worker，再检查其余节点；记录实际操作系统、内核和软件包版本，不直接套用模板版本号。

完成判定：所有节点基础检查一致；没有因为克隆产生重复身份或不兼容的虚拟 CPU。

<a id="010102-规划-cgroup资源预留和-swap"></a>

### 01.01.02 复核 cgroup、资源预留和 Swap

实施内容：复核 00 已落实的 cgroup v2、containerd systemd cgroup、关闭 Swap 和角色资源预算；只读检查不重复执行系统初始化。

过程安排：检查 stat -fc %T /sys/fs/cgroup、swapon --show、containerd config dump 和 00 重启记录；将预留参数作为 01.02.01 的 kubelet 输入。出现漂移回到 00 修复角色配置。

完成判定：主机状态与 00 交接一致，kubelet 配置可使用同一 cgroup 驱动；集群建立后再核验 Allocatable，storage 节点为 cephadm 留有预算。

<a id="010103-配置内核主机防火墙和-selinux"></a>

### 01.01.03 复核内核、防火墙和 SELinux 基线

实施内容：复验 00 已写入的模块、转发、访问规则、SELinux 模式与必要策略，不在本阶段首次修改 Linux 基线。

过程安排：对照节点初始化手册检查 sysctl、规则持久性和未处理 AVC；建立 API/CNI 后再执行相应通信检查。发现主机缺陷修改 00 的 Ansible 配置并重新验收。

完成判定：入群前主机前置符合约定；入群后真实 API、Overlay 与拒绝访问用例通过，没有为通过安装而无差别关闭安全机制。

<a id="010104-部署和验证-containerd"></a>

### 01.01.04 复验 containerd 与 CRI 交接

实施内容：核验 00 已安装并启动的 containerd/runc/crictl、systemd cgroup、registry 信任、数据挂载和 CRI 端点。

过程安排：检查 systemctl is-active containerd、crictl info、版本与 00 的 CRI smoke 结果；验证引导镜像可取回。运行时漂移回到 00 修复，禁止在 01 再维护另一份安装流程。

完成判定：RuntimeReady、镜像及凭据路径符合交接；此时允许 CNI 未安装导致 NetworkReady=false，安装 Cilium 后必须再次验证普通 Pod 网络。

### 01.01.05 处理引导镜像和仓库认证

实施内容：复核 00 已同步的 pause、API Server、Controller、Scheduler、etcd、CoreDNS、kube-vip 与 Cilium 镜像及 Digest，不在 init 过程中临时补下载。

过程安排：区分静态 Pod 引导拉取和普通 Pod 的 imagePullSecrets；使用受控只读权限或经验证的节点认证，不能假定静态 Pod 能引用普通 Secret。

完成判定：无业务 Service 和 CoreDNS 时仍能拉取引导镜像，避免初始化期间出现认证循环依赖。

## 01.02 建立控制平面与基础网络

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-02)

### 01.02.01 确定 kubeadm 集群配置

实施内容：固定 API 入口 api.k8s.internal.egon.top:6443、VIP .100、Pod CIDR、Service CIDR，保留默认 cluster.local 集群域，kubeadm networking.dnsDomain 与 kubelet clusterDomain 保持一致。

过程安排：把 API DNS、VIP、必要节点地址纳入证书 SAN；核对 kubelet DNS 指向 192.168.20.10，Service .1 不被业务占用；写入与 00 一致的 systemd cgroup、按角色的 systemReserved/kubeReserved/驱逐预算，入群后核验 Allocatable。

完成判定：初始化参数形成唯一来源；后续节点不会各用不同 Service 网段或集群域。

### 01.02.02 建立 API VIP 的引导路径

实施内容：让 kube-vip 管理控制平面 VIP，选择与当前 kubeadm 版本兼容的静态 Pod 引导顺序。

过程安排：在 cp01 初始化过程中处理所需 kubeconfig 的生成与权限，再将 VIP 接入其余控制平面；保留节点 IP 的紧急访问方法。

完成判定：VIP 可访问，初始启动没有等待尚未出现的凭据；重启后服务能够重新建立。

### 01.02.03 初始化第一个控制平面

实施内容：在 cp01 建立 stacked etcd、API Server、Controller Manager 和 Scheduler。

过程安排：检查静态 Pod、证书、etcd、本地健康状态与管理访问；记录 CNI 尚未安装时暂时 NotReady 的预期现象。

完成判定：控制平面 API 可用；能够区分正常引导中间状态与真正安装失败。

### 01.02.04 建立敏感信息加密和审计起点

实施内容：为 API 中的敏感数据规划静态加密，记录加密配置、密钥保管和审计日志位置。

过程安排：在其余控制平面接入前完成一致性设计；备份密钥并控制文件权限，禁止把完整 Secret 内容写入普通审计日志。

完成判定：三控制平面使用一致的加密策略；恢复文件不只有 etcd 数据而缺少解密密钥。

### 01.02.05 安装 Cilium 基础 CNI

实施内容：第一条主线使用经过验证的 Overlay 与 kube-proxy 共存配置，指定 Cluster Pool 与每节点 /24 地址块。

过程安排：让 Cilium 成为明确的 Pod IPAM 管理者；核对与 kubeadm 网段一致，不同时启用互相矛盾的 IPAM 配置。

完成判定：Cilium 和 CoreDNS 达到健康状态；普通 Pod 能获取地址，节点进入 Ready。

### 01.02.06 加入第二和第三控制平面

实施内容：让 cp02、cp03 分别在另外两台 ESXi 加入控制平面，形成三个 etcd 成员。

过程安排：顺序加入、逐台检查成员健康和证书；传递凭据采用受控短时方式，不将管理员材料长期留在共享目录。

完成判定：etcd 三成员组成健康多数派，三个 API 端点均可用，VIP 可以完成接管。

### 01.02.07 加入七个 Worker 并设置角色

实施内容：加入 infra01/02、storage01/02/03、worker01/02，登记节点角色和实际 ESXi 故障域。

过程安排：为存储角色增加调度保护并预留 Ceph 资源；确认必要 CNI 和系统 DaemonSet 能容忍相关污点。

完成判定：十节点全部 Ready；普通业务不会无意占满存储节点，必要系统组件不被污点阻挡。

### 01.02.08 配置集群访问与恢复管理员

实施内容：为 Mac 和管理机建立独立 kubeconfig，严格区分常规只读、实验运维和紧急管理员身份。

过程安排：设置权限、Context 和证书到期记录；保存可离线使用的恢复账户，不把管理员配置分发给所有 CI 任务。

完成判定：能够安全切换集群身份；从普通工作站操作时不会误用长期最高权限。

本节行为核对：[K02](../arch/references.md#k02)、[N01](../arch/references.md#n01)。

实施内容：分别解析测试 Service、service.namespace.svc.cluster.local 名称、kubernetes.default.svc.cluster.local 以及 harbor.k8s.internal.egon.top。

完成判定：备份材料完整可读取；不把对多个运行中的 etcd VM 分别拍快照当作一致恢复方案。

## 01.04 建立核心实验空间与 Pod 生命周期

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-04)

### 01.04.01 建立实验命名空间与应用基准

实施内容：为核心资源实验建立独立命名空间、统一标签、轻量镜像和基准响应接口。

过程安排：准备可控制启动时间、健康状态、退出行为和请求耗时的测试服务；限制资源与访问，避免故障测试触及基础平台。

完成判定：后续实验能复用同一可观察应用，不必等待正式多语言 CI。

### 01.04.02 观察 Pod、容器状态和重启

实施内容：验证 Pending、Running、Succeeded、Failed 等阶段，并观察容器 Waiting、Running、Terminated。

过程安排：制造镜像名错误、应用退出和资源不足；将 CrashLoopBackOff 等等待原因与 Pod phase 分开记录。

完成判定：能够从调度事件、容器退出码和日志定位失败层次，不把所有状态混为一谈。

### 01.04.03 实施 Init Container 与 Sidecar

实施内容：使用初始化任务准备数据或等待前置条件，再加入日志或代理 Sidecar。

过程安排：比较普通多容器模式与所选版本支持的原生 Sidecar 生命周期；检查资源、退出顺序和主容器启动依赖。

完成判定：初始化失败能够阻止主服务启动；Sidecar 不会无期限阻挡正常退出而无人察觉。

### 01.04.04 验证临时容器与故障诊断

实施内容：为无 Shell 的业务镜像设计受控调试方式，检查临时容器权限、网络和进程可见性。

过程安排：模拟无法解析、连接失败或应用卡顿，使用诊断镜像定位并记录；调试权限只给授权身份。

完成判定：能够排查精简镜像问题；不会把为调试开放的权限永久授予普通应用。

### 01.04.05 观察 OOMKilled、Eviction 与终止

实施内容：设置受限实验负载，分别触发容器内存超限、节点压力和正常终止。

过程安排：对照退出信息、事件和重调度情况；节点压力只在指定 Worker 上进行，完成后释放压力。

完成判定：可以区分内核杀进程、kubelet 驱逐和应用主动退出，并恢复节点到正常状态。

本节行为核对：[K04](../arch/references.md#k04)。

## 01.05 配置 Startup、Liveness、Readiness 与 PreStop

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-05)

### 01.05.01 验证 Startup Probe 的启动保护

实施内容：为慢启动应用设置 Startup Probe，与运行期探针使用不同判定目标。

过程安排：逐步增加启动时长，观察成功前其他探针是否被抑制、超出容忍窗口后的重启；记录阈值与真实启动分布。

完成判定：启动容忍时间有测量依据；慢启动不再被不合理的存活检查反复打断。

### 01.05.02 验证 Liveness Probe 的自愈边界

实施内容：使用本地健康信号识别进程卡死，不把所有外部数据库故障都当作应用必须重启的证据。

过程安排：注入进程假死和依赖超时两类故障，比较重启是否改善问题，防止探针导致重启风暴。

完成判定：真正失活可以恢复；依赖整体中断不会无意义地同时重启所有业务副本。

### 01.05.03 验证 Readiness 与 EndpointSlice

实施内容：让服务启动、准备完成和暂时不可服务三个状态可控，观察流量是否被路由到就绪端点。

过程安排：在持续请求期间切换 Readiness，核对 EndpointSlice 条件、已有连接与新连接的行为。

完成判定：未就绪副本不接收正常新业务流量；Readiness 失败不会被误认为必然触发重启。

### 01.05.04 实现 PreStop 与应用优雅终止

实施内容：让应用处理 SIGTERM，配置请求排空、后台任务停止和足够的终止宽限期。

过程安排：对长请求、消息消费者和正常短请求分别测试删除；PreStop 耗时算入总宽限期，不依赖钩子总能完整执行。

完成判定：终止期间的请求和消息结果可追踪；优雅终止失败时有超时与幂等补偿设计。

### 01.05.05 比较探针协议和误判

实施内容：在当前版本支持范围内对比 HTTP、TCP、Exec、gRPC 探针的检查含义和成本。

过程安排：让端口仍开但业务失败、依赖失败但进程正常等情况逐一发生，观察探针误判。

完成判定：能够按应用特征选择健康信号，而不是对所有服务复用同一个端口存活检查。

本节行为核对：[K05](../arch/references.md#k05)、[K04](../arch/references.md#k04)。

## 01.06 研究 RC、ReplicaSet 与 Deployment

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-06)

### 01.06.01 比较 RC 与 ReplicaSet

实施内容：用独立实验分别创建历史 RC 和 ReplicaSet，研究副本、Selector 和控制器接管行为。

过程安排：删掉一个受控 Pod，观察控制器补副本；刻意准备标签不匹配的 Pod，避免实验控制器使用重叠 Selector。

完成判定：理解副本控制和标签选择；RC 仅作历史对照，不进入正式业务模板。

### 01.06.02 建立 Deployment 与版本记录

实施内容：让 Deployment 管理 ReplicaSet 和 Pod，记录对象所有权、模板变化与修订版本。

过程安排：发布两个可区分响应的版本，再修改只影响副本数的字段，对比是否创建新 ReplicaSet。

完成判定：能够解释 Deployment 的版本历史来自何处，以及何种变更触发新的发布。

### 01.06.03 实施手动扩缩容

实施内容：在同一 Deployment 上变更副本数，观察调度、资源不足、服务端点与终止过程。

过程安排：在正常资源与容量不足两种场景中测试；记录缩容时未完成请求和本地临时数据的处理。

完成判定：扩容能增加实际可用副本，缩容后没有遗留资源；副本数不被等同于节点数。

### 01.06.04 比较 RollingUpdate 与 Recreate

实施内容：分别使用滚动更新和先停后建，配置可用副本、峰值副本和就绪稳定时间。

过程安排：在持续流量下改变镜像，测量错误率、发布耗时和临时资源需求；资源不足时检查为何滚动更新阻塞。

完成判定：两种策略的可用性和容量代价可比较；不会仅凭配置名称宣称零停机。

### 01.06.05 验证暂停、继续、失败和回滚

实施内容：针对错误镜像、失败探针和新版本异常分别设计发布失败场景。

过程安排：观察进度状态和历史记录，暂停后修正或选择旧版本恢复；记录是否保留了回滚所需镜像与配置。

完成判定：回滚恢复业务而不是只变更控制器状态；不假定 Deployment 会自动回滚所有失败。

### 01.06.06 区分普通滚动更新与灰度发布

实施内容：建立两版本同时存在的最小实验，使用独立标签和 Service 区分流量目标。

过程安排：先说明当前仅验证副本与入口分离；带权路由、指标分析和自动回退在 Phase 02、04 完成。

完成判定：普通更新与真正的流量灰度不被混淆，后续发布实验具有清晰前置接口。

## 01.07 验证 StatefulSet 与 DaemonSet

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-07)

### 01.07.01 建立 StatefulSet 稳定身份

实施内容：部署带 Headless Service 的小型 StatefulSet，验证序号、主机名、DNS 和有序启动。

过程安排：本阶段使用可丢弃数据，只验证身份和调度；明确暂未获得业务级持久化保证。

完成判定：Pod 重建后身份符合 StatefulSet 设计；DNS 使用 cluster.local。

### 01.07.02 比较 StatefulSet 更新与扩缩策略

实施内容：实验 OrderedReady、允许的并行管理、RollingUpdate、OnDelete 和分区更新。

过程安排：制造一个未就绪副本观察推进顺序；记录卡住后需要的修复动作，不把 Deployment 的发布参数直接套用。

完成判定：能够解释为何更新或缩容停在特定序号；实际持久卷回收留待 Phase 03 验证。

### 01.07.03 部署 DaemonSet 并验证节点覆盖

实施内容：在授权节点部署轻量守护进程，观察新节点、节点标签变化和污点对覆盖范围的影响。

过程安排：区分节点级运行需求与普通副本扩缩容，控制权限和资源消耗。

完成判定：目标节点按预期存在对应 Pod；未授权节点不会因为宽泛容忍而被自动覆盖。

### 01.07.04 实施 DaemonSet 更新和回滚

实施内容：对比 RollingUpdate 与 OnDelete，记录更新过程、ControllerRevision 和历史保留。

过程安排：发布失败版本后恢复到已验证版本，确认每个目标节点的镜像与就绪状态。

完成判定：回滚不是只修改一处标签；所有应运行节点均恢复，遗留异常版本被识别。

## 01.08 研究删除传播、所有权与 Finalizer

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-08)

### 01.08.01 比较 Foreground 与 Background 删除

实施内容：建立 Deployment、ReplicaSet、Pod 的清晰所有权链，并分别执行两种级联策略。

过程安排：记录父对象和子对象的删除顺序、可见状态与延迟，避免与普通副本自愈混在同一实验。

完成判定：能够说明不同传播策略对对象存在时间的影响，子资源没有意外遗留。

### 01.08.02 实施 Orphan 非级联删除

实施内容：让父控制器被移除但子对象保留，观察 ownerReferences 与后续控制状态。

过程安排：在独立命名空间内实验新控制器接管，核对 Selector；完成后显式清理孤儿资源。

完成判定：非级联删除的保留对象可追踪；没有多个控制器争夺同一批 Pod。

### 01.08.03 观察 Finalizer 与删除保护

实施内容：准备带 Finalizer 的测试对象，观察进入删除流程后仍保留的情况。

过程安排：确认控制器应先完成外部清理；只有核实相关外部资源和风险后，才将人工移除 Finalizer 作为恢复实验。

完成判定：不会把强制移除 Finalizer 当通用修复，删除不会静默遗留云资源或数据。

本节行为核对：[K06](../arch/references.md#k06)。

## 01.09 实现 Job、CronJob 与基础 HPA

[本专题具体操作、配置与检查](../ops/01-kubernetes/README.md#01-09)

### 01.09.01 部署批处理 Job

实施内容：为有输入和输出的任务设置完成数、并行度、重试、超时和结果保留。

过程安排：注入可重试与不可重试失败；让任务使用幂等标识，观察失败重试是否重复写入。

### 01.09.02 部署 CronJob 并处理时间语义

实施内容：为定时任务明确时区、错过调度的期限、历史保留与并发策略。

过程安排：分别实验 Allow、Forbid、Replace 和暂停恢复；用短周期测试，不把 CronJob 视为严格的恰好一次调度器。

完成判定：重复执行、错过执行和前一任务未结束时的行为均已记录；业务任务具备幂等保护。

### 01.09.03 建立资源指标入口

完成判定：HPA 所需指标可取得；此组件与 Phase 05 的 Prometheus 长期监控职责明确。

### 01.09.04 实施 CPU 与内存 HPA 基础实验

过程安排：观察 CPU 使用率相对 Request 的计算、指标缺失和缩容稳定窗口；内存实验注意缓存保留导致负载消退但内存不下降。

完成判定：扩缩容有数据支持，不发生无界扩容；高级指标、KEDA 与缩零留待 Phase 06。
