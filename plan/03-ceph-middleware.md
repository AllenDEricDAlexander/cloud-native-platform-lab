# Phase 03｜Ceph、Kubernetes 存储与有状态数据平台

文档版本：V3.0。状态：未执行。步骤数：48。

在 Rocky Linux 上由 cephadm 独立运行 Ceph，通过 Rook External 与 Ceph CSI 向 Kubernetes 供应 RBD/CephFS 卷，RGW 通过 S3 端点提供对象能力，再建设数据库与消息中间件。

前置条件：Phase 00–02 主线完成，存储节点、物理故障域、原始数据盘、镜像、时间与网络已核实。重要数据有独立备份位置。

实施边界：不使用 vSAN。三个 Ceph VM 兼任受限 Worker 只是实验资源复用，不构成完全独立的物理存储集群；Ceph 的停止、维护和升级不由 kubelet 负责。

## 03.01 确认存储硬件与数据保护边界

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-01)

### 03.01.01 复核 OSD 设备与物理故障域

实施内容：为 storage01/02/03 逐一登记 OS 盘、拟用 OSD 盘、VM 虚拟设备、Datastore、RAID 与物理宿主机。

过程安排：确认盘上没有需保留的数据、文件系统或其他集群签名；任何不确定设备停止使用，不按设备名猜测用途。

完成判定：每块 OSD 盘有唯一映射和可用确认，所有破坏性初始化都限制在已批准的实验盘。

### 03.01.02 制定容量与副本预算

实施内容：初期每台约 800GB OSD、三份副本仅作为容量示例；实际值按可用磁盘重新计算。

过程安排：同时计算原始、逻辑、快照、日志、数据重建和底层 Datastore 余量；不使用薄置备超售掩盖物理空间不足。

完成判定：可承诺容量低于理论三副本逻辑上限，写入与重建水位有明确中止阈值。

### 03.01.03 明确三故障域的恢复限制

实施内容：在三个故障域上规划副本数 3、最小可写副本数 2 的实验池，并记录降低冗余时的风险。

过程安排：单故障域丢失后可验证降级服务，但剩余两个域不能凭空重建第三个独立域副本；恢复原域或增加新域后才能恢复完整保护。

完成判定：实验报告不会把降级可写等同于已经恢复三副本容错。

### 03.01.04 保护宿主机和 Ceph 资源

实施内容：为 MON、MGR、OSD、MDS、RGW 和 kubelet 分别规划内存与 CPU，控制存储节点上的普通 Pod。

过程安排：核对 cephadm 自动内存调节策略；使用主机级资源边界与 kubelet 预留协调，不让两套调度者各自使用全部内存。

完成判定：高内存服务共置风险受控，Ceph 进程不会因为 Worker 宣告过多可用资源而持续 OOM。

本节行为核对：[S03](../arch/references.md#s03)。

## 03.02 部署独立 cephadm 集群

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-02)

### 03.02.01 准备宿主机容器和 Ceph 依赖

实施内容：在存储节点准备 cephadm 所需系统组件、Podman、时间同步、LVM 与网络规则。

过程安排：与 Kubernetes 的 containerd 区分数据目录、生命周期和日志；确认两者重启不会互相清理容器或网络配置。

完成判定：Podman 管理 Ceph，containerd 管理 K8s，职责可在主机上清楚辨认。

### 03.02.02 引导首个 Ceph 管理节点

实施内容：从内网镜像建立初始 Ceph 集群，生成 FSID、管理凭据和初始 MON/MGR。

过程安排：限制初始管理入口，登记生成的身份与密钥；先验证健康，再接入其余主机，不开放匿名管理界面。

完成判定：首个节点可管理且配置可备份，初始身份不会因为重复引导而意外改变。

### 03.02.03 扩展为三个 MON 与两个 MGR

实施内容：将三台不同 ESXi 上的存储 VM 加入 Ceph，分布 MON 多数派和 MGR 主备。

过程安排：逐节点检查时钟、认证、端口、版本和管理连通性；在多数派健康时完成主备切换试验。

完成判定：监视器具有三个独立 VM/物理域成员，管理面主备切换结果有记录。

### 03.02.04 按明确设备清单创建 OSD

实施内容：仅对已核实的设备建立 OSD，采用显式设备选择，避免自动吞掉所有空盘。

过程安排：一次处理一个节点，观察设备准备、OSD 加入、CRUSH 位置与集群状态，再处理下一个。

完成判定：OSD 与批准清单一致，系统盘、管理数据盘和 Rook 对比实验盘未被误用。

### 03.02.05 配置 CRUSH、池与基础监控

实施内容：将真实故障域映射到 CRUSH 放置策略，建立独立业务池并评估 PG 自动管理。

过程安排：核对跨主机副本分布、pool size/min_size 和健康告警；内置 Dashboard 与监控接口限于内网。

完成判定：副本确实分散到不同物理宿主机，告警与实际风险对应。

### 03.02.06 建立 Ceph 配置与凭据备份

实施内容：备份 FSID、主机与服务规格、MON 信息、CRUSH、池定义和必需密钥。

过程安排：保存至独立位置并加密；禁止把生产级管理员 keyring 作为所有 Kubernetes 工作负载通用凭据。

完成判定：丢失单个管理节点后有恢复材料，备份读取权限与日常业务权限分离。

本节行为核对：[S01](../arch/references.md#s01)、[S02](../arch/references.md#s02)。

## 03.03 提供 RBD、CephFS 与 RGW

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-03)

### 03.03.01 建立 RBD 块存储池

实施内容：为数据库和通用块卷规划专用池、RBD 功能和配额，核对内核客户端支持。

过程安排：先用可丢弃卷验证创建、映射、格式化、读写和释放；实际客户端功能以选定版本验证。

完成判定：块卷生命周期可控，映射和卸载不遗留锁或设备占用。

### 03.03.02 建立 CephFS 与 MDS 主备

实施内容：为共享文件需求建立独立文件系统、元数据池、数据池和 MDS。

过程安排：验证多客户端并发读写、权限、配额和 MDS 切换；不要将多个数据库进程指向同一个共享数据目录。

完成判定：RWX 共享文件能力可用，并与数据库主从复制的语义明确区分。

### 03.03.03 建立 RGW 对象存储入口

实施内容：为 s3.svc.internal.egon.top 提供受控 RGW 入口，按客户端能力选择路径式或虚拟主机式访问。

过程安排：配置 Bucket、用户、权限、TLS 和生命周期；若使用虚拟主机式访问，额外规划 Bucket 域名和证书覆盖。

完成判定：S3 客户端能完成上传、读取、权限拒绝和删除，未默认启用公开 Bucket。

### 03.03.04 区分对象存储与灾备目的地

实施内容：可将 RGW 用于构建缓存、Loki/Tempo 数据和实验对象，但不得作为本 Ceph 唯一灾备。

过程安排：记录同故障域的便利副本与真正外部备份的区别；将关键数据定期复制到独立存储。

完成判定：整个 Ceph 不可用时，恢复必需文件仍可取得。

## 03.04 接入 Rook External 与 Ceph CSI

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-04)

### 03.04.01 准备外部集群最小权限连接

实施内容：为 Kubernetes 消费端建立限定池、文件系统和操作范围的 Ceph 身份。

过程安排：通过当前 Rook 支持的导出与导入流程获取连接信息；分别核对 cephadm 集群版本、Rook 和 CSI 兼容性。

完成判定：K8s 无需掌握 Ceph 全局管理员密钥，仍可供应授权范围的卷。

### 03.04.02 部署 Rook External 控制与 CSI

实施内容：安装外部模式需要的 Rook/CSI 组件，不在消费集群中重新初始化 MON 或 OSD。

过程安排：确认 CSI 的实际安装入口，避免 Helm 与 Operator 重复创建同一套驱动；节点插件具有必需而非无限的主机权限。

完成判定：驱动注册正常、无重复组件，Ceph 守护进程仍由 cephadm 管理。

### 03.04.03 检查所有卷消费者的 Ceph 网络

实施内容：从所有可能承载业务的节点验证 MON、OSD 与 CephFS 客户端通信。

过程安排：按真实源地址配置访问控制；不能只允许 .106–.108 三台存储节点而阻断其他 Worker 的 CSI 数据路径。

完成判定：业务 Pod 无论调度在哪个允许节点，都能访问同一持久卷。

### 03.04.04 建立 StorageClass 与默认策略

实施内容：建立 ceph-rbd 和 cephfs 两类主要 StorageClass，明确池、权限、绑定模式、回收与扩容策略。

过程安排：初始只指定一个默认类；数据库模板显式选择块存储，共享文件应用显式选择 CephFS。

完成判定：PVC 不会因为多个默认类或模板遗漏而落入意外存储。

### 03.04.05 验证 RWO、RWOP 与 RWX

实施内容：用受控测试卷比较同节点多 Pod、跨节点及独占 Pod 的访问行为。

过程安排：核对 RWOP 对当前 CSI 的支持；说明 RWO 限制的是单节点读写，不自动保证仅一个 Pod 使用。

完成判定：应用按需要选对访问模式，不依赖名称缩写猜测数据隔离。

本节行为核对：[S03](../arch/references.md#s03)、[S04](../arch/references.md#s04)。

## 03.05 完整验证 PV、PVC 与快照生命周期

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-05)

### 03.05.01 比较静态 PV 与动态供应

实施内容：分别使用预建资源和 StorageClass 自动创建资源，观察绑定、容量、访问模式与状态变化。

过程安排：在独立 Namespace 测试不匹配条件和 Pending；记录 PV、PVC 与 Ceph 后端对象的对应关系。

完成判定：可以定位绑定失败原因，每个卷都能追溯到实际存储对象。

### 03.05.02 验证卷扩容与文件系统变化

实施内容：对测试 PVC 增加容量，观察存储端、CSI、节点和文件系统的各层进度。

过程安排：核对 StorageClass 扩容设置及在线支持；不把缩小 PVC 作为常规可用功能。

完成判定：应用实际看到新增空间，扩容失败时能区分后端和客户端阶段。

### 03.05.03 部署快照控制链并还原测试数据

实施内容：核对 VolumeSnapshot CRD、Snapshot Controller、CSI snapshotter 和 SnapshotClass。

过程安排：写入已知数据后创建快照，再恢复到新 PVC 并验证；记录快照一致性是否经过应用冻结或数据库协同。

完成判定：能够从快照恢复数据，但不把崩溃一致性自动当作数据库事务一致性。

### 03.05.04 验证克隆、回收与保留策略

实施内容：比较测试卷克隆、Retain、Delete 和 Snapshot 删除策略，观察后端资源是否仍存在。

过程安排：同时核对 StatefulSet 的 PVC 保留策略与 Operator 行为；它们与 PV 回收策略是不同层面的决定。

完成判定：删应用、删 PVC、删 PV 和删快照的实际结果分别得到验证，重要数据不会被误联动清理。

### 03.05.05 验证 Pod 迁移和卷重新挂载

实施内容：让带 PVC 的业务从一个 Worker 迁移到另一个，记录卸载、挂载、应用恢复与数据一致性。

过程安排：在节点失联情形下先确认原写入者已经停止或被隔离，再处理强制分离；不得在旧节点仍可能写入时强制双挂。

完成判定：避免双写和损坏，恢复流程包含必要的隔离或 fencing 判断。

### 03.05.06 回访 StatefulSet 持久化实验

实施内容：使用 volumeClaimTemplates 完成固定身份、每副本独立卷、更新、缩容与删除测试。

过程安排：对比 Phase 01 的临时数据实验，确认 Pod 重建和 PVC 保留是不同问题。

完成判定：每个序号的业务数据可追踪，StatefulSet 删除后存储去留符合已配置策略。

## 03.06 实施存储故障与 Rook 自管理对照

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-06)

### 03.06.01 演练单 OSD 和存储 VM 故障

实施内容：先使用可丢弃数据，分别停止 OSD 服务和一台存储 VM。

过程安排：观察 MON 多数派、降级 PG、业务延迟与恢复；同时认识到 VM 故障也会移除其 Kubernetes Worker。

完成判定：故障影响范围、可写状态、重建条件和恢复时间都有实测，不把虚拟盘故障等同物理坏盘。

### 03.06.02 演练计划维护和安全下线

实施内容：分别规划 kubelet Drain、Ceph 服务维护、OSD 下线与 VM 重启，避免误认为一种维护动作会处理所有层次。

过程安排：确认剩余多数派和数据状态后再操作；设置会到期或会被主动撤销的维护标志，防止长期阻止恢复。

完成判定：维护结束后所有标志、调度与健康状态恢复，数据没有长期处于未保护状态。

### 03.06.03 测试容量水位和恢复限速

实施内容：在专用测试池验证配额、接近水位告警和恢复流量对业务的影响。

过程安排：限制数据量与停止阈值，不填满真实 Datastore；在 HDD/1GbE 条件下控制 Ceph 重建与 CI 并发。

完成判定：可以识别容量风险和恢复压力，实验不会把底层物理盘写满导致全平台故障。

### 03.06.04 准备 Rook 自管理独立实验资源

实施内容：使用另外的空盘或临时虚拟机建立 Rook 内部 Ceph 对照，禁止复用主 Ceph OSD。

过程安排：为不同 FSID、资源名称、设备选择和故障域建立清单；资源不足时停用其他重型模块后再开展。

完成判定：两套 Ceph 的设备、凭据和默认 StorageClass 不发生交叉。

### 03.06.05 实验 CephCluster 与存储 CRD

实施内容：在内部模式创建 CephCluster、CephBlockPool、CephFilesystem、CephObjectStore 等适用资源。

过程安排：观察 Operator 如何调谐守护进程、扩容、恢复和升级，与 cephadm 的主机规格管理对比。

完成判定：理解内部 Operator 与外部消费模式的责任差异，不期待 External 模式接管外部 OSD。

### 03.06.06 安全清理内部 Ceph 对比实验

实施内容：先删除测试工作负载、验证没有需保留数据，再按实验生命周期释放卷、池、集群和设备。

过程安排：清理只作用于单独的实验资源；检查 Finalizer 和卸载状态，记录需要的人工确认点。

完成判定：主 Ceph 不受影响，实验盘与 API 对象不存在无法追溯的残留。

本节行为核对：[S04](../arch/references.md#s04)。

## 03.07 建设 PostgreSQL 与关系型数据库实验

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-07)

### 03.07.01 部署单实例 PostgreSQL 基准

实施内容：先用独立 PVC 建立轻量 PostgreSQL，定义用户、数据库、连接参数和测试数据。

过程安排：从测试应用完成事务、连接池、重启和数据校验；禁止应用使用数据库超级用户进行所有业务。

完成判定：掌握基础持久化和客户端行为后再增加 HA 复杂度。

### 03.07.02 使用 CloudNativePG 建立高可用

实施内容：部署匹配版本的 CloudNativePG，配置跨物理域实例、独立卷、读写入口和复制。

过程安排：比较单实例与多实例资源需求；检查 Pod 反亲和、Ceph 物理域及实际放置，不只看副本数量。

完成判定：主备拓扑、角色和客户端入口清楚，故障后写入目标能跟随新主。

### 03.07.03 实施 WAL 归档、备份与 PITR

实施内容：核对当前 CloudNativePG 支持的备份插件与对象存储配置，定义保留和加密策略。

过程安排：创建基线备份后持续归档 WAL，写入可识别事务，再恢复到指定时间的新实例。

完成判定：恢复出的事务边界经过比对；WAL 和全量备份都能从独立位置取回。

### 03.07.04 演练数据库故障切换与升级

实施内容：让客户端持续写入，分别模拟主 Pod、主 Worker 和底层暂时延迟故障。

过程安排：观察选主、连接重试、同步与异步复制的丢失窗口；数据库大版本升级采用官方支持路线，不只更换镜像。

完成判定：实测 RPO/RTO 与客户端恢复行为有记录，应用回滚不会错误回滚数据库结构。

### 03.07.05 增加 MySQL Operator 对照

实施内容：在独立命名空间使用经核对的 MySQL Operator 和受控数据集；需要集群外客户端访问时，使用 mysql.svc.internal.egon.top 映射到受控的内网数据库入口。

过程安排：比较生命周期、复制、备份、故障切换和资源占用；与 PostgreSQL 共享实验规范但不强制复制配置参数。

完成判定：获得可复用的关系型数据库对照结果，测试后按规则回收资源。

## 03.08 建设 Redis、Kafka、RabbitMQ 与 NATS

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-08)

### 03.08.01 部署 Redis 并验证持久化

实施内容：从独立单实例开始验证缓存访问、TTL、淘汰、RDB/AOF 与重启。

过程安排：根据当前版本核对配置和许可证；缓存数据、业务不可丢数据及持久化策略分别定义。

完成判定：可以解释重启后的数据结果，不能把 Redis 一律当成永久可靠数据库。

### 03.08.02 比较 Sentinel、Redis Cluster 与 Valkey

实施内容：分别建立主从加 Sentinel 和分片集群，使用实际客户端测试发现、切换与分片。

过程安排：Valkey 作为独立兼容对比，不静默替换用户要求的 Redis；比较客户端、持久化和许可差异。

完成判定：主备高可用与分片扩容的差异明确，每种模式有自己的恢复记录。

### 03.08.03 使用 Strimzi 部署 Kafka KRaft

实施内容：部署匹配的 Strimzi，采用 KRaft，规划 Controller/Broker 角色、监听器、证书、存储与副本。

过程安排：先用低负载拓扑，再按资源许可测试高可用；检查 advertised listeners 和跨节点客户端可达性。

完成判定：生产者和消费者可以稳定连接所有需要的 Broker，未依赖不完整的单端口代理。

### 03.08.04 验证 Kafka 数据与消费者生命周期

实施内容：实验 Topic、Partition、副本、ISR、Consumer Group、Offset、重平衡和 Lag。

过程安排：模拟 Broker 停止、消费者重启及积压，测试确认级别和幂等策略；为 Phase 06 KEDA 留下可复用积压场景。

完成判定：消息数量、重复和恢复位置可校验，未把任意配置都声称为恰好一次处理。

### 03.08.05 使用 RabbitMQ Operator 建立消息集群

实施内容：定义受控 RabbitMQ 集群、管理权限、用户、虚拟主机、证书和 Quorum Queue。

过程安排：验证 Publisher Confirm、消费确认、重投、死信和队列策略；分散副本并注意磁盘水位。

完成判定：消息去向可追踪，管理控制台不公开，持久消息在约定故障条件下可恢复。

### 03.08.06 测试 RabbitMQ 故障与队列积压

实施内容：分别模拟消费者崩溃、节点失败和慢消费者，观察重投与队列长度。

过程安排：让业务消费具备幂等性并控制预取；记录恢复后的重复处理与吞吐。

完成判定：得到事件扩缩容所需指标和可靠消费方案，而不是只测试消息能发送。

### 03.08.07 部署 NATS 与 JetStream

实施内容：先验证轻量 Pub/Sub 和 Request/Reply，再引入 JetStream 流、持久消费者和复制。

过程安排：比较与 Kafka、RabbitMQ 的确认、保留、重放和运维成本；不按项目名称假定功能完全对等。

完成判定：同一个简单业务场景可以在三种消息系统上重放并比较。

## 03.09 开发 Operator 并完成数据平台交接

[本专题具体操作、配置与检查](../ops/03-ceph-middleware/README.md#03-09)

### 03.09.01 设计自定义 DemoApp API

实施内容：定义 DemoApp 的期望状态、实际状态、条件、资源所有权和删除策略。

过程安排：只管理一个小型应用的 Deployment、Service 和 ConfigMap，避免第一版控制器直接管理整个集群。

完成判定：API 字段和错误状态能表达实际业务需求，作用域与权限边界明确。

### 03.09.02 实现调谐、幂等与 Finalizer

实施内容：选择 Go Kubebuilder、Java Fabric8 或 Rust kube-rs 之一完成主要实现，其余工具链作为比较。

过程安排：验证重复事件、资源已存在、部分失败、重试和删除；状态写入避免造成无限调谐。

完成判定：控制器能持续把实际状态收敛到期望，故障后重复执行不会制造重复资源。

### 03.09.03 验证 CRD 版本与控制器权限

实施内容：为测试 API 规划 schema、状态更新、RBAC 和未来版本演进。

过程安排：测试无效输入、缺权限和旧版本对象；转换与升级在隔离数据上进行。

完成判定：Operator 拥有最小权限，升级不会悄悄破坏已有自定义资源。

### 03.09.04 建立数据平台启停与恢复顺序

实施内容：按存储、CSI、Operator、数据库、消息服务、应用的依赖关系记录启动与停止。

过程安排：高可用消息集群不能简单缩到零就当成安全暂停；按各项目流程备份、停止、恢复或重建。

完成判定：按需实验不破坏多数派和持久数据，基础 Ceph 保持健康。

### 03.09.05 完成 Phase 03 验收与交接

实施内容：核对 PVC 供应、块/文件/对象存储、数据库和消息故障恢复、独立备份与自研 Operator。

过程安排：向 Phase 04 提供受限连接信息、存储模板和测试数据；秘密材料单独交付，结果标注实际验证与未启用项。

完成判定：DevOps 可以依赖已验证的中间件和存储，尚未完成的 HA 或性能指标不被默认为已通过。
